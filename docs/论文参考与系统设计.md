# 论文参考驱动的数据可视化智能体设计

> **依据**：开题报告《基于 LangChain 的数据可视化智能体的设计与实现》，以及开题报告“研究进展”中引用的 8 篇相关论文。
> **目的**：逐篇提取论文中可复用的设计，说明本项目采用什么、不采用什么、为什么，最终形成可落地的系统设计。
> **边界**：本文不是论文复现，也不是文献综述；重点是把论文设计转化为本项目的模块、接口、流程和验收依据。
> **标记约定**：
> - **论文做法**：论文本身提出的方法或系统结构；
> - **本项目采用**：明确落到本项目设计中的部分；
> - **本项目不采用**：经过取舍后不纳入首版的部分，并说明原因。
>
> 需求编号沿用 `docs/依据开题设计.md`。

## 1. 设计方法

### 1.1 为什么逐篇看论文

只把论文当成“研究背景”，容易得到两个坏结果：

1. 设计文档只剩功能清单，不知道某个模块为什么存在；
2. 直接照搬某一篇论文，忽略它原本的领域、输入形态和工程约束。

因此本文对每篇论文都回答五个问题：

- 它解决的核心问题是什么？
- 它的关键设计是什么？
- 这个设计对数据可视化智能体有什么可复用价值？
- 本项目采用哪一部分，放弃哪一部分？
- 采用后落到哪个模块、接口或需求？

### 1.2 八篇论文在本设计中的角色

| 论文/系统 | 在本设计中的角色 |
|---|---|
| DataTone | 解决“用户说得不清楚，系统不能瞎猜”的问题 |
| NL4DV | 提供“自然语言 → 结构化分析规范”的中间层 |
| Chat2VIS | 证明大模型可以直接生成可视化代码，并给出提示词工程与评测思路 |
| VOICE | 提供角色化 bots、会话式探索和解释性响应思路 |
| C5 | 提供对话结构可视化与上下文连续性的设计目标 |
| RGVisNet | 提供“先检索、再修订”的检索增强生成思路 |
| FlowSense | 提供数据流工作流、上下文感知和增量编辑思路 |
| nvAgent | 提供处理器、规划器、验证器的协作与校验思路 |

### 1.3 组合后的设计主线

八篇论文不是并列堆叠，而是各自补一段链路：

```text
用户输入
  ↓
DataTone：先识别歧义，不急着生成
  ↓
NL4DV：形成结构化分析计划（ChartPlan）
  ↓
FlowSense：把计划放进可追踪的工作流，向用户展示识别结果
  ↓
RGVisNet：检索相似的可视化代码原型
  ↓
Chat2VIS：用大模型生成/修订 Pyecharts 代码
  ↓
nvAgent：校验代码、执行结果和输出
  ↓
VOICE：用会话方式解释结果、接受下一轮修改
  ↓
C5：保存并可视化上下文，保证多轮连续
```

这条主线对应本项目的核心判断：**不要让大模型从一句自然语言直接跳到最终代码，而是把“理解、计划、检索、生成、验证、解释”拆成可检查的阶段。**

## 2. 论文逐篇分析

### 2.1 DataTone：把歧义当作一等公民

**论文做法**

DataTone 关注自然语言可视化接口中的歧义问题。它采用混合主动式（mixed-initiative）方法，在“自然语言查询 → 可视化”的整个过程中建模歧义，通过算法消歧和交互式 ambiguity widgets，把系统的理解结果和可选解释展示在歧义真正影响结果的位置，让用户参与决策。

**为什么重要**

自然语言里的“销售额”“趋势”“最近”“最好的城市”都可能有多种解释。传统做法是系统内部选一个默认值，用户只能看到错误结果后重新描述；DataTone 的思路是把歧义显式化，让用户在关键节点修正。

**本项目采用**

- **必须**在图表计划中记录歧义和假设，而不是只保留一个最终答案。
- 对高置信度的解释可以自动采用，但要在结果旁说明“系统这样理解”。
- 对会显著改变图表结果的歧义，提供轻量澄清选项，例如字段选择、时间范围、聚合方式、图表类型。
- 把“澄清”放在计划阶段，而不是代码报错之后。

**本项目不采用**

- 不照搬 DataTone 的完整 ambiguity widget 体系。桌面端首版采用轻量澄清卡片/选项，不打断每一次生成。
- 不对所有歧义都强制追问，否则用户会觉得系统低效。采用“置信度 + 影响范围”双阈值：低影响自动默认，高影响才追问。

**落到设计**

`ChartPlan` 增加以下字段：

| 字段 | 含义 |
|---|---|
| `ambiguities` | 识别到的歧义列表，例如字段歧义、时间歧义、聚合歧义 |
| `assumptions` | 系统自动采用的假设，以及采用理由 |
| `confidence` | 对计划整体或关键字段的置信度 |
| `clarification` | 需要用户确认的问题和候选选项 |

对应需求：FR-15、FR-20、FR-21。

### 2.2 NL4DV：先产出分析规范，再谈画图

**论文做法**

NL4DV 是一个 Python 工具包。输入是一个表格数据集和一条自然语言查询，输出是一个 JSON 形式的 analytic specification，包含：

- 数据属性（attributes）；
- 分析任务（analytic tasks）；
- 一组与查询相关的 Vega-Lite 可视化规范。

它把自然语言理解、数据属性识别、分析任务识别和可视化编码分开，使没有 NLP 背景的开发者也能构建可视化自然语言接口。

**为什么重要**

NL4DV 证明了“自然语言到图表”不应该只有一步。中间的分析规范既是可检查的契约，也是后续渲染、修改和多方案比较的基础。

**本项目采用**

- 定义结构化的 `ChartPlan`，作为 ChartPlanSkill 的输出、ChartGenerateSkill 的输入。
- 计划中包含数据字段、分析任务、图表类型、编码通道、聚合/筛选/排序、标题和布局。
- 支持生成多个候选计划，再按数据形态和用户约束排序，而不是只生成一个计划。
- 计划先校验，再进入代码生成。

**本项目不采用**

- 不输出 Vega-Lite 规范。本项目最终使用 Pyecharts 生成 HTML，因此计划层使用与 Pyecharts 对应的图表和选项描述。
- 不要求复刻 NL4DV 的完整规则式 NLP 流程。本项目以 LLM 为主，保留确定性规则做字段匹配、类型校验和兜底。

**落到设计**

`ChartPlan` 的最小字段：

```json
{
  "plan_id": "p1",
  "title": "2024 年各城市销售额对比",
  "chart_type": "Bar",
  "data_ref": "series_sales",
  "analysis_task": "comparison",
  "dimensions": ["城市"],
  "measures": ["销售额"],
  "x": "城市",
  "y": "销售额",
  "series": [],
  "aggregation": "sum",
  "filters": [],
  "sort": {"by": "销售额", "order": "desc", "top_n": 10},
  "transform": [],
  "layout": {"width": "900px", "height": "500px"},
  "ambiguities": [],
  "assumptions": ["按销售额总和聚合"],
  "confidence": 0.92
}
```

对应需求：FR-17、FR-21、5.2。

### 2.3 Chat2VIS：大模型代码生成 + 提示词工程 + 基准评测

**论文做法**

Chat2VIS 不再训练新的语言模型，而是利用 ChatGPT、Codex、GPT-3 等预训练大模型，通过提示词工程把自由形式的自然语言直接转换成可视化代码。它强调对模糊、格式错误、多语言查询的适应能力，并用基准评测比较不同模型和提示策略。

**为什么重要**

它给出了本项目的技术可行性依据：**预训练 LLM 可以在不微调的情况下承担“自然语言 → 可视化代码”的主要工作**。同时它也暴露了一个问题：一次性生成代码很脆弱，需要提示词约束、输出清理和评测。

**本项目采用**

- 用 LLM 生成 Pyecharts 代码，而不是要求用户学习编程。
- 用结构化提示词提供数据 schema、图表计划、RAG 参考代码和输出约束。
- 对模型输出做代码围栏清理、语法检查、字段检查和执行验证。
- 建立固定测试集，统计代码生成成功率、数据一致性和多语言/模糊表达的处理效果。
- 支持多轮修改，而不是每次从零生成。

**本项目不采用**

- 不采用“用户一句话 → 直接输出代码”的单步模式。本项目在中间加入 ChartPlan、RAG 和验证器，降低不可控性。
- 首版不对大模型做领域微调；以提示词工程、RAG 和工具调用为主。

**落到设计**

代码生成提示词至少包含：

1. 系统角色和输出格式；
2. 用户需求与多轮约束；
3. 数据字段、类型、样例值和数据质量问题；
4. 已确认的 `ChartPlan`；
5. RAG 检索到的 Pyecharts 示例；
6. 代码规范（只能使用允许的库、必须 `render()`、必须使用 `opts.` 前缀等）；
7. 失败时的修复要求。

对应需求：FR-24、FR-28、FR-43、FR-44、FR-32。

### 2.4 VOICE：角色化 bots + 会话式探索 + 解释

**论文做法**

VOICE 把 LLM 的对话能力与交互式探索可视化结合起来。它的基础是一组“pack-of-bots”，不同 bot 负责不同任务，例如任务分配、指令提取、内容生成；通过微调和提示词工程让 bot 适应角色。系统支持语音命令、语音回应，并让文本解释与对应的视觉表示紧密耦合，强调低延迟和高准确率。论文应用在分子可视化领域，包含 3D 模型的交互和 flythrough 序列。

**为什么重要**

VOICE 说明“智能体”不一定要做成一个巨大的通用模型。把任务拆给角色明确的 bot，再通过会话层协调，更容易控制输出质量和响应方式。

**本项目采用**

- 中心 Agent 之下设置角色明确的 Skill/提示词：数据预览、图表计划、代码生成、验证、解释。
- 每个角色只拿自己需要的信息，避免一个提示词同时承担理解、规划、写代码和解释。
- 图表结果返回时附带简短解释：为什么选这个图、用了哪些字段、做了哪些假设。
- 预留语音输入/输出适配层；首版以文本为主，语音作为可选扩展。
- 把响应时间作为设计指标，而不是事后优化。

**本项目不采用**

- 不实现 3D 分子可视化和 flythrough；这与本项目的二维图表目标无关。
- 不把语音列为首版验收硬指标。VOICE 的语音能力是重要参考，但开题报告的预期目标以自然语言文本输入为主。
- 不做每个 bot 单独微调；首版用角色化提示词和工具边界实现。

**落到设计**

角色提示词表：

| 角色 | 输入 | 输出 | 约束 |
|---|---|---|---|
| Context Processor | 用户输入、数据摘要、历史 | 过滤后的上下文、字段候选 | 不生成图表代码 |
| Planner | 上下文、数据形态、用户约束 | `ChartPlan[]` | 必须输出结构化计划 |
| Retriever | 计划、数据 schema | 相关代码示例 | 只返回相关片段 |
| Generator | 计划、示例、代码规范 | Pyecharts 代码 | 不重新读取原始数据 |
| Validator | 计划、代码、执行结果 | 校验报告、修复建议 | 不修改用户原始数据 |
| Explainer | 计划、结果、日志摘要 | 面向用户的解释 | 不暴露内部提示词和密钥 |

对应需求：FR-51—FR-56、FR-63、NFR-01。

### 2.5 C5：上下文连续性不只是“多存几条消息”

**论文做法**

C5 是一个交互式对话可视化系统，包含 Global View、Topic View 和 Context-associated Q&A View：

- Global View 用 GitLog 式结构表示对话演化；
- Topic View 用知识图谱展示一个主题内的问答节点及关系；
- Context-associated Q&A View 用三个联动视图帮助用户深入理解单轮对话，并在提问时提供具体上下文。

论文指出多轮对话中同时存在“人的遗忘”和“模型的上下文遗忘”，目标是通过可视化提升对话理解与上下文连续性。

**为什么重要**

它提醒我们：多轮连续性不仅是把历史消息塞进 prompt，还要让用户和系统都知道“当前在哪个话题、之前确认了什么、哪些结论还有效”。

**本项目采用**

- 会话状态中保存主题、关键约束、已确认计划、已生成图表和未解决问题。
- 对话过长时生成结构化摘要，而不是简单截断。
- 在 WinUI 中提供轻量的“上下文卡片/会话提纲”，让用户看到系统记住的内容。
- 支持按主题检索历史消息，避免不同数据文件的上下文互相污染。

**本项目不采用**

- 不复刻 C5 的完整三视图对话可视化系统。对桌面端首版来说，完整的 GitLog 图和知识图谱成本过高。
- 不把 C5 误当成“记忆压缩算法”。C5 的价值是上下文可视化与理解，本项目的三层记忆是工程实现，二者是目标相近、手段不同。

**落到设计**

会话状态至少包含：

```json
{
  "session_id": "s1",
  "workspace": "sales_2024",
  "topics": [
    {
      "topic_id": "t1",
      "title": "城市销售对比",
      "active_plan_ids": ["p1"],
      "confirmed_constraints": ["只看华东", "按销售额降序"],
      "open_questions": ["是否包含其他区域"]
    }
  ],
  "summary": "用户先看了城市销售对比，后要求改成柱状图并只看前五名。",
  "recent_turns": []
}
```

对应需求：FR-46—FR-50。

### 2.6 RGVisNet：检索原型，再生成和修订

**论文做法**

RGVisNet 是面向 text-to-vis 的混合检索-生成框架。它不直接从零生成可视化查询，而是：

1. 从 DV query 代码库中检索最相关的候选作为 prototype；
2. 对 prototype 进行修订，生成目标 DV query；
3. 检索模型使用 schema-aware 的 NL 编码器和基于 GNN 的 DV query 编码器；
4. 生成模型共享编码器参数，并使用 DV grammar-aware decoder 复用检索到的 prototype。

论文在 NVBench 上报告了相对现有生成模型最高 74.28% 的整体准确率提升。

**为什么重要**

它给 RAG 提供了直接依据：与其让模型凭空写 Pyecharts 代码，不如先找“类似图表 + 类似数据结构”的已验证代码，再让模型改写。对 API 复杂、版本差异大的可视化库尤其有效。

**本项目采用**

- 建立本地 Pyecharts 代码示例库，按图表类型、数据形态、API 特性、布局方式打元数据。
- 检索查询由“用户意图 + 数据 schema + 计划中的图表类型”组成，而不是只拿用户原句去搜。
- 把检索到的示例作为“参考原型”注入生成提示词，要求模型复用结构、按当前数据和计划改写。
- 检索为空或向量库不可用时降级为无参考生成，并记录降级原因。
- 用固定样例评估检索命中率和生成成功率。

**本项目不采用**

- 不训练神经检索模型、GNN 编码器或 grammar-aware decoder。本项目用 Qwen Embedding 0.6B + Chroma 做语义检索，用 LLM 做修订。
- 不要求检索结果直接可运行；它是参考原型，不是最终答案。

**落到设计**

代码示例元数据：

| 字段 | 用途 |
|---|---|
| `chart_type` | 过滤图表类型 |
| `data_shape` | 时间序列、类别对比、构成、相关性等 |
| `api_features` | Grid、双轴、堆叠、标签、工具箱等 |
| `code` | 可参考的 Pyecharts 片段 |
| `notes` | 版本注意事项和常见错误 |
| `source` | 文档来源，便于维护 |

检索流程：

```text
用户意图 + 数据 schema + ChartPlan
  → 构造检索 query
  → Chroma top-k
  → 相关性过滤/去重
  → 注入 Generator prompt
  → 生成当前数据的代码
```

对应需求：FR-33—FR-39。

### 2.7 FlowSense：把自然语言放进数据流，而不是孤立的一次问答

**论文做法**

FlowSense 是面向数据流可视化系统的自然语言接口。它使用语义解析器，配合特殊的 utterance tagging 和 utterance placeholders，使解析结果能泛化到不同数据集和数据流图；系统会显式展示识别出的 dataset/diagram special utterances，让用户知道系统当前理解了什么；用户可以继续用自然语言扩展和调整数据流图。

**为什么重要**

它强调三件事：

1. 自然语言操作应该改变一个**可见的工作流状态**，而不是只返回一张图；
2. 系统要把识别到的数据、字段、图表类型展示出来，让用户能纠正；
3. 解析器要能处理“当前数据集特有的名字”，不能把字段名硬编码进语法。

**本项目采用**

- 把 DataPreview → ChartPlan → ChartGenerate 设计成显式工作流，有状态、有阶段、可回退。
- 在界面上展示系统识别到的数据表、字段、时间列、指标、图表类型和假设，形成“上下文感知”。
- 支持增量修改：用户可以在现有计划上改图表类型、字段、排序、标题，而不是每次重新开始。
- 对字段名、表名使用占位符/实体链接，避免把某个数据集的列名写死进提示词或规则。

**本项目不采用**

- 不使用 CoreNLP/SEMPRE 这套传统语义解析栈；本项目以 LLM 解析为主，配合确定性的字段匹配和 schema 校验。
- 不复刻 VisFlow 的数据流图编辑器；本项目的“工作流”以阶段状态和计划编辑的形式呈现。

**落到设计**

工作流状态：

```text
idle
  → ingesting（读取文件/数据库/多模态）
  → profiling（清洗、结构识别、预览）
  → planning（意图解析、ChartPlan）
  → clarifying（可选：歧义确认）
  → retrieving（RAG）
  → generating（代码生成）
  → validating（计划/代码/执行/输出校验）
  → rendering（HTML 落盘）
  → done / failed
```

界面必须显示当前阶段和已识别上下文，避免用户面对“黑盒等待”。

对应需求：2.1、3.8、FR-51—FR-55、FR-68。

### 2.8 nvAgent：处理器、规划器、验证器的协作

**论文做法**

nvAgent 面向 NL2Vis，特别是需要跨多表推理的复杂查询。它由三个 agent 组成：

- **Processor Agent**：数据库处理与上下文过滤；
- **Composer Agent**：规划可视化生成；
- **Validator Agent**：代码翻译与输出验证。

系统通过迭代式数据交互和验证，提升单表和多表场景的表现。论文在 VisEval 基准上报告了单表 7.88%、多表 9.23% 的提升。

**为什么重要**

它说明“规划”和“验证”都应该是一等阶段，而不是生成失败后的补救。尤其是多表场景，先过滤上下文、再规划、再验证，比让一个模型一次性完成所有事情更稳。

**本项目采用**

- 三个核心 Skill 与 nvAgent 的角色划分对齐：
  - DataPreviewSkill ≈ Processor Agent 的数据处理/上下文过滤；
  - ChartPlanSkill ≈ Composer Agent 的规划；
  - ChartGenerateSkill + Validator ≈ Validator Agent 的代码翻译与输出验证。
- 在代码生成后执行多层次验证：计划字段存在性、代码语法、运行结果、HTML 是否有效、图表数据是否为空。
- 验证失败进入修复循环，保留失败代码和错误信息。
- 多表/多数据源时先做上下文过滤，避免把所有表塞进提示词。

**本项目不采用**

- 不做三个完全自主、自由对话的 agent。首版采用“中心 Agent + Skill + 明确验证阶段”，减少不可控的 agent 间协商。
- 不把 Validator 做成只会说“错了”的模型；它必须输出可执行的修复建议和结构化错误。

**落到设计**

验证层次：

| 层次 | 检查内容 | 失败处理 |
|---|---|---|
| 计划校验 | 字段是否存在、类型是否匹配、x/y 是否为空、多图是否重复 | 回到 Planner 修正 |
| 代码静态检查 | 语法、禁止的库、是否调用 `render()`、是否使用 `opts.` | 回到 Generator 修复 |
| 运行检查 | 是否抛异常、是否超时、是否产生空数据 | 带错误栈修复 |
| 输出检查 | HTML 是否存在、是否非空、是否包含图表容器 | 重新渲染或修复 |
| 数据检查 | 图表中的数据是否来自 `df`、是否出现明显空值/全零 | 回到计划或数据阶段 |

对应需求：FR-21、FR-28、FR-30、FR-51—FR-55。

## 3. 横向对比与设计结论

### 3.1 八篇论文的取舍总表

| 论文 | 核心贡献 | 本项目采用 | 本项目不采用 | 主要风险 |
|---|---|---|---|---|
| DataTone | 混合主动式歧义管理、ambiguity widgets | 计划中记录歧义/假设，关键歧义轻量澄清 | 完整 widget 体系、每次强制追问 | 过度追问降低效率 |
| NL4DV | 自然语言 → 结构化 analytic specification | `ChartPlan` 中间层、候选计划、计划校验 | Vega-Lite 输出、完整规则式 NLP | 计划 schema 可能限制复杂图表 |
| Chat2VIS | LLM + 提示词工程直接生成可视化代码 | Pyecharts 代码生成、输出清理、基准评测 | 单步直出代码、领域微调 | 模型幻觉、API 版本差异 |
| VOICE | 角色化 bots、会话探索、解释、低延迟 | 角色化提示词、解释性响应、可选语音 | 3D flythrough、强制语音、逐 bot 微调 | 角色过多导致编排复杂 |
| C5 | 对话结构可视化、上下文连续性 | 会话提纲、主题/约束摘要、上下文卡片 | 完整三视图对话分析系统 | 上下文展示增加 UI 复杂度 |
| RGVisNet | 检索原型 + 修订生成 | 本地代码示例 RAG、schema-aware 查询、降级 | 神经检索/GNN/grammar decoder | 检索质量决定增强效果 |
| FlowSense | 数据流工作流、上下文感知、增量编辑 | 显式工作流状态、实体展示、计划增量修改 | CoreNLP/SEMPRE、VisFlow 编辑器 | 状态机设计过重 |
| nvAgent | 处理器/规划器/验证器协作、迭代验证 | 三阶段 Skill + Validator + 修复循环 | 自由自治多 agent | 验证成本与延迟增加 |

### 3.2 共识流程

八篇论文指向同一条工程上更稳的流程：

```text
自然语言输入
  → 上下文过滤（FlowSense / nvAgent Processor）
  → 歧义识别与假设（DataTone）
  → 结构化计划（NL4DV / nvAgent Composer）
  → 计划校验（NL4DV / nvAgent Validator）
  → 代码示例检索（RGVisNet）
  → 代码生成/修订（Chat2VIS）
  → 执行与输出验证（nvAgent Validator）
  → 解释与下一轮修改（VOICE / C5）
```

这条流程的关键不是“多几个 agent”，而是**每个阶段都有明确的输入、输出和失败处理**。

### 3.3 从论文得到的设计原则

1. **中间表示优先**：自然语言先变成计划，再变成代码。
   来源：NL4DV、nvAgent。
   对应：ChartPlan、计划校验。

2. **歧义显式化**：系统可以猜，但必须让用户知道它猜了什么。
   来源：DataTone。
   对应：`ambiguities`、`assumptions`、澄清卡片。

3. **检索增强、可降级**：先找相似代码原型，再让模型改写；检索失败不能阻断生成。
   来源：RGVisNet。
   对应：Qwen Embedding + Chroma、top-k、fallback。

4. **角色化而不是万能提示词**：理解、规划、生成、验证、解释分开。
   来源：VOICE、nvAgent。
   对应：中心 Agent + Skill + 角色提示词。

5. **验证是一等阶段**：计划、代码、运行结果、HTML 都要校验。
   来源：nvAgent、Chat2VIS。
   对应：Validator、修复循环、失败产物。

6. **上下文要可见、可管理**：多轮对话不仅存消息，还要有主题、约束和摘要。
   来源：C5、VOICE。
   对应：会话状态、上下文卡片、长期记忆。

7. **工作流要可追踪**：用户能看到当前阶段和系统识别到的数据/字段。
   来源：FlowSense。
   对应：状态机、阶段日志、实体展示。

8. **评测要工程化**：不只看“图能不能出来”，还要看数据对不对、类型是否合理、耗时和 token 是否达标。
   来源：Chat2VIS、RGVisNet、nvAgent。
   对应：测试集、成功率、数据一致性、延迟、token。

### 4.6 提示词设计

提示词按角色拆分，不把所有信息塞进一个模板。

| 提示词 | 必须包含 | 必须避免 |
|---|---|---|
| Context Processor | 用户输入、数据字段、历史摘要 | 让模型直接写代码 |
| Planner | 数据 schema、数据形态、用户约束、歧义规则 | 让模型输出自然语言长文代替计划 |
| Retriever Query | 图表类型、分析任务、字段名、数据形态 | 只使用用户原句 |
| Generator | 计划、示例、代码规范、数据读取契约 | 让模型重新读取原始文件 |
| Validator | 计划、代码、错误、可用字段 | 只说“失败”不给修复建议 |
| Explainer | 计划、假设、结果摘要 | 暴露内部提示词、密钥、完整日志 |

提示词块顺序建议：

```text
[系统角色与边界]
[用户需求]
[数据 schema 与数据质量]
[已确认的 ChartPlan]
[RAG 参考代码]
[代码/输出规范]
[失败修复要求（仅重试时）]
```

### 4.7 RAG 设计

**语料**

- Pyecharts 官方示例和项目内已验证代码；
- 按图表类型、数据形态、API 特性分类；
- 文档有明确的 `source` 和版本说明。

**切分**

- 一个示例一个 chunk，避免把多个图表类型混在一起；
- 长示例按“配置 + 绘图 + 渲染”切分，但保留图表类型和 import 信息；
- 元数据随 chunk 存储，检索后可按 `chart_type` 过滤。

**查询**

```text
query = 用户意图关键词
      + 数据形态（时间序列/类别/构成/相关性）
      + 图表类型
      + 需要的 API 特性（多系列、堆叠、双轴、Grid）
```

**检索与注入**

- top-k 召回；
- 按图表类型、数据形态做相关性过滤；
- 去重后取少量高质量示例；
- 注入 Generator 提示词，并明确“参考结构，不要照抄数据字段”。

**降级**

- 向量库不可用、embedding 失败、无命中：继续生成，提示“无参考示例”；
- 记录检索耗时、命中数量和降级原因。

### 4.8 记忆设计

| 层 | 内容 | 存储 | 使用方式 |
|---|---|---|---|
| 短期 | 当前会话最近若干轮消息 | 内存/会话状态 | 直接进入上下文 |
| 中期 | 主题、约束、计划、图表、未解决问题 | 结构化摘要 | 压缩后进入提示词 |
| 长期 | 会话文件、历史摘要、产物索引 | 文件 | 重启恢复、按主题检索 |

规则：

- 不以“固定截断”作为唯一压缩手段；
- 主题切换时保留旧主题摘要，但当前提示词只带相关主题；
- 用户确认过的约束优先级高于模型推断；
- 会话文件不记录 API Key、数据库密码等敏感信息。

### 4.9 验证与修复

```text
Plan
  → 字段存在性/类型/编码校验
  → Code
  → 语法/禁用库/渲染调用检查
  → Execute
  → 异常/超时/空数据检查
  → HTML
  → 文件存在/非空/图表容器检查
  → Data
  → 关键字段和数值抽样核对
```

修复策略：

1. 计划错误：回到 Planner，带上校验错误和可用字段；
2. 代码错误：回到 Generator，带上错误栈和失败代码；
3. 运行超时：降低数据量或简化图表，记录降级；
4. 输出为空：检查数据过滤和聚合，必要时回到计划；
5. 多次失败：停止自动修复，返回可读错误和失败产物。

### 4.11 非功能设计

| 维度 | 设计 |
|---|---|
| 性能 | 单次任务目标 ≤120 秒；检索、生成、执行分别记录耗时 |
| 成本 | 单份任务 token ≤0.3M；历史压缩、RAG 限量、避免重复调用 |
| 可靠性 | 单阶段失败不破坏已完成结果；失败可重试、可追踪 |
| 安全 | API Key/数据库密码不入库、不入日志；数据库只读；代码执行超时和隔离 |
| 可测试性 | 假模型/假向量库可跑回归；真实模型测试单独标记 |
| 可维护性 | Skill 契约稳定；提示词、RAG 语料、图表规则可独立更新 |

## 5. 关键设计决策

| 编号 | 决策 | 论文依据 | 需求 | 取舍 |
|---|---|---|---|---|
| D1 | 自然语言先转 `ChartPlan`，再生成代码 | NL4DV、nvAgent | FR-17、FR-21 | 增加一次模型调用，但换来可校验性 |
| D2 | 计划中记录歧义、假设和置信度 | DataTone | FR-20 | 需要 UI 配合，否则用户看不到 |
| D3 | 代码生成前检索 Pyecharts 示例 | RGVisNet | FR-33—FR-39 | 依赖知识库质量；检索失败要降级 |
| D4 | 角色化提示词/Skill，而非万能提示词 | VOICE、nvAgent | FR-51—FR-56 | 编排复杂度上升 |
| D5 | 生成后必须经过 Validator | nvAgent | FR-28、FR-30 | 增加延迟，但显著降低静默错误 |
| D6 | 多轮上下文用结构化摘要，不只存消息 | C5 | FR-47—FR-50 | 需要维护会话状态 |
| D7 | 工作流状态和识别结果对用户可见 | FlowSense | FR-68、FR-65 | UI 信息密度增加 |
| D8 | 语音作为可选扩展，不纳入首版硬验收 | VOICE | FR-59、FR-66 | 控制范围，避免范围蔓延 |
| D9 | 多智能体收敛为中心 Agent + Skill + Validator | nvAgent、VOICE | FR-51—FR-56 | 放弃自由协作的灵活性，换取可控性 |
| D10 | 用固定测试集评估成功率、数据一致性、耗时和 token | Chat2VIS、RGVisNet、nvAgent | NFR-01—NFR-03 | 需要维护测试数据 |

## 6. 评测设计

### 6.1 测试集

| 类型 | 样例 | 目的 |
|---|---|---|
| 单表 | CSV/Excel 时间序列、类别对比、构成、相关性 | 基础图表能力 |
| 多表 | 一个文件多个 sheet、多数据源 | 上下文过滤和多表选择 |
| 多模态 | 表格截图、扫描 PDF、Office 内嵌表格 | 抽取与数据保真 |
| 歧义 | “最好的城市”“最近的数据”“销售额” | 歧义识别和澄清 |
| 多轮 | “改成柱状图”“只看前五名”“加标题” | 上下文连续性 |
| 错误注入 | 字段不存在、代码报错、模型超时 | 验证与修复 |
| 复杂图表 | 多系列、堆叠、双轴、Grid | RAG 和代码生成 |

### 6.2 指标

| 指标 | 定义 | 目标 |
|---|---|---|
| 代码执行成功率 | 生成代码可执行并产出非空 HTML | ≥90% |
| 数据一致性 | 图表关键数值与源数据一致 | 抽样核对，不允许系统性错误 |
| 图表类型匹配 | 计划类型与数据形态/用户意图一致 | 人工评估 + 规则检查 |
| 计划有效率 | 计划字段/类型/编码通过校验 | 尽可能高，失败可修复 |
| 歧义处理 | 高影响歧义被识别并说明/澄清 | 关键样例全覆盖 |
| 检索命中率 | top-k 中包含可用示例的比例 | 按知识库评估 |
| 响应时间 | 提交到 HTML 可预览 | ≤120 秒 |
| token | 单次任务总消耗 | ≤0.3M |
| 修复率 | 首次失败后自动修复成功比例 | 记录并持续提升 |
| 用户可用性 | 普通用户完成主流程 | 用户测试 |

### 6.3 评测方法

- 自动化：脚本提交固定任务，检查产物、字段、耗时、token；
- 半自动：规则检查 + 人工抽查图表可读性；
- 消融：去掉 RAG、去掉 Validator、去掉计划层，比较成功率；
- 多模型：DeepSeek、GLM 等 OpenAI 兼容模型对比；
- 多轮：固定对话脚本，检查约束是否保持。

## 7. 风险与应对

| 风险 | 表现 | 应对 |
|---|---|---|
| 计划 schema 过窄 | 复杂图表无法表达 | 允许 `extra` 扩展字段；计划校验只强制核心字段 |
| RAG 检索不准 | 注入无关示例，误导模型 | 元数据过滤、top-k 限制、相关性阈值、降级 |
| 模型幻觉字段 | 代码引用不存在列 | 计划校验 + 代码字段检查 + 错误修复 |
| 验证成本高 | 每次生成多轮调用，延迟上升 | 分层校验；静态检查优先；只在失败时调用修复 |
| 上下文膨胀 | 多轮后 token 超限 | 结构化摘要、主题隔离、按需检索 |
| 过度澄清 | 用户频繁被打断 | 置信度 + 影响范围双阈值 |
| 代码执行安全 | 生成代码访问文件/网络 | 超时、隔离、只读数据、路径限制 |
| 语音范围蔓延 | 首版无法交付 | 语音只做可选适配层，不进入硬验收 |
| C5 式 UI 过重 | 界面复杂、开发量大 | 首版只做上下文卡片/会话提纲 |

## 9. 结论

八篇论文分别解决不同问题，单独照搬任何一篇都不足以支撑本项目的完整链路：

- 只有 DataTone，会得到“会追问”的系统，但缺少结构化计划和代码生成；
- 只有 NL4DV，会得到分析规范，但缺少大模型代码生成和多轮交互；
- 只有 Chat2VIS，会得到一次性代码生成，但缺少歧义管理、检索和验证；
- 只有 RGVisNet，会得到检索增强，但缺少工程化工作流和桌面端；
- 只有 nvAgent，会得到协作/验证思路，但仍需结合本项目的 LangChain、MCP、WinUI 和本地 RAG。

因此本项目的设计结论是：

> **以 NL4DV 的计划中间层为骨架，以 DataTone 的歧义管理保证理解正确，以 RGVisNet 的检索增强提高代码生成质量，以 Chat2VIS 的 LLM 代码生成作为执行手段，以 nvAgent 的验证器保证结果可靠，以 FlowSense 的工作流和上下文感知组织流程，以 C5/VOICE 的记忆与会话设计保证多轮体验。**

这比“用一个提示词让大模型直接画图”更复杂，但每个复杂点都对应一个可测试的失败模式，也更符合开题报告对“可控、可追溯、可扩展”的要求。
