# 数据视图设计（ViewSpec / 执行器 / 确定性保证）

## 1. 核心抽象

```text
DataView = 纯函数(DataFrame..., params) -> DataFrame
```

一个 view 由三样东西定义，缺一不可：

| 项 | 内容 | 来源 |
|---|---|---|
| `inputs` | 1..n 个不可变 dataset（含 hash） | 接入层产物 |
| `spec` | 声明式变换：SQL 或插件引用 | 用户显式给出 / LLM 生成一条 / 默认（空 = 直通） |
| `engine_version` | 执行器版本（影响结果语义的都要进版本） | 代码常量 |

```text
view_id = sha256(source_hash + spec_hash + engine_version)
```

**同一 view_id 必得同一 DataFrame**——这是整个方案唯一需要维护的不变量。
同一 spec 被第二次请求时直接命中缓存，不重算；prompt 相同 + 数据相同 → 同 view_id，
即使背后是 LLM 生成的 spec，重复运行也稳定。

## 2. ViewSpec

```json
{
  "kind": "sql",
  "sql": "select 月份, sum(销售额) as 销售额 from d1 group by 月份 order by 月份",
  "params": {},
  "inputs": ["ds_ab12cd34ef56.table_0"],
  "engine": "sqlite"
}
```

两种 kind：

### 2.1 `sql`（默认）

- 一条**只读** `SELECT / WITH ... SELECT`；复用 `service/data_ingestion/sql_safety.py` 的
  `ensure_read_only()`：剥字符串/注释后校验，禁 DDL/DML/多语句/PRAGMA/ATTACH；
- 表名按 `inputs` 注册进引擎（SQLite 内存库，`to_sql` 注入；后端可换）；
- 排序要么写进 SQL，要么由执行器按声明的 `order_by` 补齐——**不允许无稳定排序的输出**；
- 参数只允许绑定占位符（`:p` 风格），不允许字符串拼接。

### 2.2 `plugin`

```json
{
  "kind": "plugin",
  "name": "kline_resample",
  "version": 3,
  "params": {"rule": "1min"},
  "inputs": ["ds_ab12cd34ef56.table_0"]
}
```

契约：`plugins/data_view/<name>.py` 暴露 `apply(df, params) -> pd.DataFrame`，且：

1. **纯函数**：输入只有 `df` 和 `params`；禁 `random`、`datetime.now()`、文件/网络 IO、
   全局可变状态、读取 df 之外的任何数据；
2. **显式 params**：所有影响行为的量都从 `params` 来，无隐式默认漂移（签名里不写非耦合默认值）；
3. **声明 schema**：函数旁挂 `OUTPUT_SCHEMA`，声明输出列名/角色，执行器校验；
4. **版本化**：文件内声明 `VERSION`，函数语义改动必须递增，否则缓存继续命中旧结果。

安全实现：插件文件在启动时扫描注册，禁止运行期动态加载用户上传的代码；
LLM 只能引用已注册的 `name + version`，不能提交新函数体。

## 3. 执行器

```text
service/data_view/
├── spec.py        # ViewSpec dataclass、hash、校验
├── engine.py      # 执行：数据注册、SQL/插件分派、稳定排序、行数统计
├── cache.py       # view_id -> parquet 落盘/命中（runtime/datasets/<ds>/views/）
└── registry.py    # 插件扫描与注册
```

引擎选型：**默认 SQLite（零新增依赖）**；大表场景后端可换 DuckDB（可选依赖，P2 再谈），
对 ViewSpec 透明——engine 字段声明，结果语义以 spec 为准，不依赖引擎方言能力。

执行流程：

```text
resolve inputs（dataset hash 校验）
  → spec 校验（只读 SQL / 已注册插件 + schema 声明）
  → 缓存命中？ → 读 parquet 返回
  → 执行 → 输出校验（OUTPUT_SCHEMA / 行数>0，允许显式声明可空）
  → 物化到 runtime/datasets/<ds>/views/<view_id>.parquet + manifest.json
  → 返回 view_id + schema
```

**物化不落盘的失败**：spec 校验失败、执行抛错、输出 schema 不符——
一律返回结构化错误（带 spec 摘要与原因），不缓存失败结果，不静默降级。

## 4. 与 series 的关系

**series 就是 view 的物化产物**，不需要新对象：

- 接入层现有 path（reader → 归一化 → splitter）产出的每条 series，是 `kind=identity` 的默认 view：
  spec 为空、view_id 即数据文件 hash；
- 派生 view 是第二类 series：`view_id` 进 manifest，`extra_semantics.view_spec` 留摘要，
  供规划阶段判断"这条 series 是怎么来的"；
- plan 仍然引用 `series_id`（即 view 的 series 身份），**plan schema 不改**；
  生成代码继续拿注入的 `df`，不知道也不关心数据来自原始表还是派生 view；
- 用户没提特殊加工 → 不创建派生 view，链路与今日完全一致。

## 5. 确定性保证清单

| 保证 | 实现点 |
|---|---|
| 同 spec 同数据 → 同结果 | view_id 内容寻址；spec hash 含 params、插件版本、引擎版本 |
| 输出顺序稳定 | SQL 必须带 order_by 或显式声明"无序可接受"；插件契约要求排序稳定 |
| 无隐藏状态 | 插件纯函数契约 + 注册期静态审查（禁 IO/随机/时间） |
| 失败可见 | 三类失败（校验/执行/schema）都有结构化错误码，不静默 |
| 可审计 | manifest 记录 inputs、spec、engine_version、产出行数、耗时 |
| 可回退 | 原始 series 永不覆盖；view 失效直接弃用，不影响任何已有产物 |

## 6. LLM 的角色边界

- **可以**：根据用户 prompt 生成一条 SQL / 引用一个插件（含 params）；
- **不可以**：提交任意 Python 函数体、绕过 spec 直接执行 pandas、
  在生成图表代码里自造数据读取（现有"禁止自写数据读取"契约继续生效）；
- LLM 生成的 spec 进入执行路径前必须过 schema 与只读校验；
  校验失败把错误原文回给 agent 重试一次，仍失败则任务失败并说明原因——
  不允许"LLM 输出什么就执行什么"。

## 7. 明确不做的（防反模式回潮）

- 不做 fitness / 图表契约 / 策略引擎 / 多 variant 对比——判图能力在生成层，已存在；
- 不做固定 op 枚举——spec 表达能力即能力；
- 不做 dry-run/confirm 双态工作流——派生 view 默认可逆（原 series 还在），
  无需确认协议；数据丢失类操作（Top-N 截断）由 spec 里的显式 SQL 表达，用户可读可改；
- 不让 view 层处理"图表好不好看"——那是 prompt 规则 / chart_polish / 技能的职责；
- 不在本目录里堆积业务列名或阈值。
