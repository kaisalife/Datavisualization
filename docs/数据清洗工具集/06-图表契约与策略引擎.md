# 图表契约与策略引擎

本文回答两个问题：

1. 什么叫“这套数据能画这张图”？
2. 同一问题有多个处理办法时，怎么做到既灵活又不失控？

核心答案：**图表契约（Chart Contract） + 可视化意图（Visual Intent） + 可组合策略（Preparation Strategy）**。
契约定义“图需要什么”，意图定义“用户想表达什么”，策略定义“在约束下怎么准备”。

## 1. 为什么需要图表契约

如果只写“数据质量规则”，会出现两个极端：

- 规则太松：什么问题都只报告，agent 仍然不知道怎么画；
- 规则太死：把某一种业务口径写进代码，换一份数据就误判。

图表契约把“图的要求”变成显式、可配置、可测试的数据：

```text
Line 需要：>=2 个有序 x 点、>=1 个数值 y、允许缺失断点、允许负值
Pie 需要：1 个数值指标、2..6 个非负类别、类别之间互斥、合计有意义
Bar 需要：1 个类别轴、>=1 个数值指标、类别过多要 Top-N/分组
Histogram 需要：1 个数值指标、足够观测值、分箱策略
Scatter 需要：2 个数值指标、成对缺失处理、样本上限
```

这样一来：

- `assess_visual_fitness` 不再靠 LLM 猜“能不能画”；
- `propose_preparation` 能针对具体 blocker 生成策略；
- 新增图表类型只需要加契约，不需要改 MCP 协议；
- 测试可以逐条验证“什么数据应该 ready / needs / not_fit”。

## 2. VisualIntent：用户到底想画什么

`VisualIntent` 是准备层的输入，不是图表代码。它允许“自动”，但关键约束必须显式。

```json
{
  "chart_type": "Pie",
  "analysis_task": "composition",
  "x_role": "category",
  "y_roles": ["measure"],
  "group_by": null,
  "max_categories": 6,
  "max_points": 50,
  "time_grain": "auto",
  "aggregation": {
    "default": "sum",
    "rate_like": "mean"
  },
  "missing_policy": "report",
  "unit_policy": "keep",
  "sort": "auto",
  "constraints": {
    "must_keep": ["北京", "上海"],
    "must_exclude": ["合计"],
    "allow_information_loss": false,
    "preserve_totals": false
  }
}
```

字段说明：

| 字段 | 作用 | 默认 |
|---|---|---|
| `chart_type` | 目标图表；`auto` 表示让推荐器决定 | `auto` |
| `analysis_task` | trend / comparison / composition / distribution / relationship | 从 chart_type 推导 |
| `x_role` / `y_roles` | 轴的角色期望，不绑定具体列名 | 由契约推导 |
| `group_by` | 分组维度；为空表示不分组 | `null` |
| `max_categories` / `max_points` | 可读性上限；为空用契约默认 | 契约默认 |
| `time_grain` | 时间粒度；`auto` 按数据与图表选择 | `auto` |
| `aggregation` | 聚合口径；按指标语义选择 | sum / mean |
| `missing_policy` | report / gap / drop / fill_explicit | `report` |
| `unit_policy` | keep / split / convert_explicit | `keep` |
| `sort` | auto / asc / desc / natural | `auto` |
| `constraints` | 用户硬约束 | 空 |

### 2.1 意图不是“业务规则”

- `must_keep` / `must_exclude` 是用户约束，不是代码里的业务列名；
- `aggregation` 可以由用户指定，也可以由指标名语义（率/均价/计数）推导；
- `unit_policy=convert_explicit` 必须带目标单位，不能只写“自动换算”。

## 3. ChartContract：图的要求

### 3.1 Schema

```json
{
  "id": "pie",
  "chart_type": "Pie",
  "analysis_tasks": ["composition"],
  "required": {
    "measures": 1,
    "axis": "categorical",
    "non_negative": true,
    "min_categories": 2,
    "max_categories": 6,
    "min_points": 2
  },
  "limits": {
    "max_categories": 6,
    "max_series": 1,
    "max_points": 12,
    "max_label_length": 18
  },
  "policies": {
    "missing": "drop_axis",
    "duplicates": "aggregate",
    "negative": "block",
    "zero": "allow",
    "totals": "exclude",
    "units": "keep",
    "sort": "desc"
  },
  "operations": {
    "allowed": ["exclude_rows", "aggregate", "top_n", "other_bucket", "sort_rows", "truncate_labels"],
    "forbidden": ["fill_missing", "dedupe_keep_first", "convert_unit"]
  },
  "validators": [
    "has_measure",
    "has_category_axis",
    "non_negative",
    "category_count",
    "no_negative_share"
  ],
  "aliases": ["pie", "环形图", "饼图"]
}
```

字段说明：

| 字段 | 含义 |
|---|---|
| `required` | 硬性要求；不满足为 `not_fit` 或 `needs_preparation` |
| `limits` | 可读性上限；超过为 warning，通常可由操作解除 |
| `policies` | 默认处理口径；可被意图/skill 覆盖 |
| `operations.allowed` | 允许的准备操作白名单 |
| `operations.forbidden` | 明确禁止的操作，防止 agent 绕过契约 |
| `validators` | 可执行的检查函数名；与信号码分离，便于复用 |
| `aliases` | 中文/英文别名，供意图解析 |

### 3.2 内置契约建议

| 图表 | 硬性要求 | 关键限制 | 默认策略 |
|---|---|---|---|
| `Line` | 有序 x、>=1 数值 y、>=2 点 | 点数过多重采样；缺失保留断点 | 负值允许；重复时间聚合 |
| `Area` | 同 Line，且基线有意义 | 堆叠时不能有负值混叠 | 构成型面积图需非负 |
| `Bar` | 类别轴、>=1 数值 y | 类别 >12 建议 Top-N/横向 | 合计排除；重复聚合 |
| `Pie` | 1 指标、2–6 非负类别 | 不能有负值；不能有重复类别 | 合计排除；Top-N + 其他 |
| `Treemap` | 1 指标、非负、层级可选 | 类别 2–20；单层隐藏面包屑 | 同 Pie |
| `Histogram` | 1 数值指标、>=5 观测 | 分箱策略；缺失排除 | 不自动删异常值 |
| `Boxplot` | 1 数值指标、>=5 观测 | 离群点标记而非删除 | 可叠加散点 |
| `Scatter` | 2 数值指标、成对缺失 | 样本上限；避免过度绘制 | 缺失成对删除需说明 |
| `Heatmap` | 2 个维度/数值轴、矩阵密度 | 空格处理；颜色范围 | 缺失保留空格 |
| `Candlestick` | 时间 + OHLC 四列、时间有序 | 不能跨粒度聚合 | 缺口保留/标记 |
| `Radar` | 多指标同量纲/可归一化 | 量纲不一致需先处理 | 单位不同不自动归一 |
| `Funnel` | 阶段有序、非负、单指标 | 阶段不能重复/乱序 | 排序 |
| `Gauge` | 单指标 + 范围 | 多指标需拆图 | 不适用多维数据 |

> 这些是默认建议，最终以 `configs/visualization_contracts.json` 为准。
> 不在 Python 里散落 `if chart_type == "Pie" and ...`。

### 3.3 契约加载与覆盖

```text
configs/visualization_contracts.json       # 项目默认
skills/<name>/visual_contract.json         # 领域覆盖（可选）
请求里的 visual_intent                     # 单次任务覆盖
```

优先级从高到低：

1. 请求 `visual_intent` 的显式字段；
2. skill 的 `visual_contract.json`；
3. 项目默认契约；
4. 代码兜底（只允许最保守的 ready 判定）。

覆盖只允许改字段，不允许删除 `validators`；否则会出现“为了让图通过，把检查删掉”的漏洞。

## 4. Fitness：怎么判断 ready / needs / not_fit

### 4.1 三种状态

| 状态 | 含义 | 后续动作 |
|---|---|---|
| `ready` | 当前数据可以直接表达目标图 | 进入规划/生成 |
| `needs_preparation` | 有可执行的准备策略，处理后可变 ready | 生成 2–4 个策略并预览 |
| `not_fit` | 当前数据/图型组合在语义上不成立（如负值饼图、无指标） | 改图型或明确告知用户 |

`not_fit` 不是“数据错误”，而是“这张图不该这样画”。

### 4.2 评估结果

```json
{
  "series_id": "sales_2024.销售额",
  "intent": {"chart_type": "Pie", "analysis_task": "composition"},
  "status": "needs_preparation",
  "signals": [
    {"code": "VIS_HIGH_CARDINALITY", "severity": "warn", "column": "城市", "count": 40},
    {"code": "VIS_NEGATIVE_FOR_PART", "severity": "blocker", "column": "销售额", "count": 3}
  ],
  "fitness": {
    "Pie": "needs_preparation",
    "Bar": "needs_preparation",
    "Line": "ready"
  },
  "best": "Line",
  "alternatives": ["Bar"],
  "reason": "负值不能表达份额；40 个类别超过饼图可读上限；折线图可直接表达趋势",
  "strategies": [
    {"strategy_id": "pie_filter_top6", "requires_confirmation": true},
    {"strategy_id": "bar_top10_other", "requires_confirmation": true},
    {"strategy_id": "line_all", "requires_confirmation": false}
  ]
}
```

### 4.3 评估顺序

1. **硬性要求**：无指标、无轴、全空、负值饼图 → 先判 `not_fit`；
2. **可修复问题**：高基数、重复时间、合计行、缺失 → `needs_preparation`；
3. **可读性**：标签长度、点数、量级差 → warning + 视图建议；
4. **数据量/性能**：样本上限、分块 → 只影响展示，不改变状态。

## 5. 策略引擎：从信号到可执行方案

### 5.1 策略不是规则，是模板

一个策略由“操作序列 + 约束 + 取舍”组成：

```json
{
  "strategy_id": "pie_top6_other",
  "label": "Top 6 + 其他",
  "applies_to": ["VIS_HIGH_CARDINALITY"],
  "operations": [
    {"op": "exclude_rows", "params": {"mode": "total_rows"}},
    {"op": "top_n", "params": {"column": "城市", "n": 6, "other": true}}
  ],
  "impact": {
    "information_loss": "medium",
    "rows_affected": 34,
    "preserves_negative": true
  },
  "requires_confirmation": true,
  "pros": ["保留饼图", "扇区可读"],
  "cons": ["34 个城市合并为其他", "用户看不到长尾明细"]
}
```

### 5.2 策略生成流程

```text
signals + intent + constraints
        │
        ▼
匹配策略模板（按 signal code / chart type）
        │
        ▼
过滤：违反用户约束 / 契约 forbidden / 数据不支持
        │
        ▼
排序：信息损失小 -> 改动小 -> 更符合意图
        │
        ▼
截断到 max_strategies（默认 3）
        │
        ▼
dry-run 计算 affected / fitness_after / preview
```

### 5.3 排序原则

不是“最干净”优先，而是：

1. **不改数据**（视图操作）优先；
2. **不改总量**（长转宽、排序、拆分单位列）优先；
3. **改动可解释**（聚合、重采样）次之；
4. **有信息损失**（Top-N、排除行、去重）再次；
5. **改变数值含义**（单位换算、填充、派生）最后，且必须确认。

用户显式要求可以改变排序，例如“我就要饼图，其他无所谓”。

### 5.4 策略矩阵（可扩展）

| 信号 | 策略 A | 策略 B | 策略 C |
|---|---|---|---|
| `VIS_HIGH_CARDINALITY` | Top 10 + 其他 | 横向条形 | 按上级维度分组 |
| `VIS_TIME_DUPLICATE` | 按时间 sum | 按时间 mean | 按业务键拆多系列 |
| `VIS_TIME_GAP` | 保留断点 | 重采样到更高粒度 | 补时间轴（确认） |
| `VIS_MISSING_VALUES` | 保留缺口 | 删除缺失点 | 按组填充（确认） |
| `VIS_TOTAL_ROWS` | 排除合计 | 单独总计卡 | 保留并标注 |
| `VIS_NEGATIVE_FOR_PART` | 改 Bar/Line | 过滤负值（说明） | 正负分图 |
| `VIS_UNIT_MIXED` | 拆单位列 | 分图 | 换算（确认） |
| `VIS_SCALE_MISMATCH` | 分图 | 双轴 | 对数轴（视图） |
| `VIS_OUTLIER_DOMINATES` | 对数轴 | 缩放窗口 | 单独标注 |
| `VIS_TOO_MANY_POINTS` | 重采样 | 缩放窗口 | 显示层抽样 |
| `VIS_LONG_LABELS` | 截断 | 换行 | 横向条形 |

> 策略矩阵本身也可以放在 `configs/visualization_strategies.json`，由 skill 扩展。
> 代码只负责匹配和执行，不把业务选择写死。

## 6. 灵活性从哪里来

### 6.1 意图可覆盖

同一个 series，不同意图得到不同准备：

```text
intent=Pie, max_categories=6   → Top 6 + 其他
intent=Bar, max_categories=12  → Top 12 + 其他
intent=Line, max_points=200    → 不截断类别，改用重采样/缩放
intent=Line, allow_information_loss=false → 只建议视图操作
```

### 6.2 契约可配置

- 图表上限、缺失策略、允许操作都在 JSON；
- 新增图表类型只加契约；
- 领域差异用 skill 覆盖，不改核心代码；
- 测试直接读契约，避免“代码和文档不一致”。

### 6.3 操作可组合

策略不是固定函数，而是操作序列：

```json
[
  {"op": "exclude_rows", "params": {"mode": "total_rows"}},
  {"op": "aggregate", "params": {"by": ["月份"], "agg": {"销售额": "sum"}}},
  {"op": "sort_rows", "params": {"by": ["月份"], "order": "asc"}},
  {"op": "axis_scale", "params": {"axis": "y", "scale": "log"}}
]
```

任何操作都可以 dry-run，返回实际影响；组合顺序由策略决定，不由 LLM 自由拼接。

### 6.4 视图与数据分离

| 类型 | 是否改变 parquet | 例子 |
|---|---|---|
| 数据操作 | 是 | 聚合、Top-N、过滤、单位换算 |
| 视图操作 | 否 | 对数轴、标签截断、缩放窗口、双轴 |

这样既能让图好看，又不会为了好看改数据。图表生成代码只读取数据操作后的 parquet；
视图操作写进 plan 的 `view_transforms`，由生成阶段应用。

### 6.5 策略可比较

`compare_preparations` 返回：

```json
{
  "variants": [
    {"variant_id": "v1", "strategy": "bar_top10_other", "fitness": {"Bar": "ready"}, "information_loss": "medium", "rows": 11},
    {"variant_id": "v2", "strategy": "line_all", "fitness": {"Line": "ready"}, "information_loss": "none", "rows": 1200},
    {"variant_id": "v3", "strategy": "area_by_region", "fitness": {"Pie": "ready"}, "information_loss": "low", "rows": 7}
  ],
  "recommended": "v2",
  "reason": "用户要求保留完整趋势；v2 不丢数据，且 Line 已 ready"
}
```

### 6.6 扩展点

| 扩展 | 方式 | 是否需要改核心 |
|---|---|---|
| 新图表类型 | 新增 `configs/visualization_contracts.json` 条目 + 必要操作 | 否 |
| 领域策略 | `skills/<name>/visual_contract.json` / `visual_strategies.json` | 否 |
| 新操作 | 在 `operations.py` 注册纯函数；必须带影响统计和 dry-run | 是（少量） |
| 新信号 | 在 `profile.py` 计算 + 在契约里引用 | 是（少量） |
| 外部抽取器 | `visual/adapters.py` + feature flag | 是（隔离） |

> 不允许通过“任意 Python 表达式”扩展策略。扩展点必须是命名操作或声明式配置，
> 否则无法审计，也无法保证 Windows/沙箱安全。

## 8. 反模式

- **把业务列名写进契约**：契约只描述角色（measure/category/time），不写“销售额”“城市”；
- **把阈值散落在代码里**：所有上限、比例、最少点数都进配置；
- **用 LLM 决定是否丢数据**：LLM 可以建议策略，丢数据必须结构化确认；
- **用视图操作掩盖数据问题**：对数轴不能把负值变成可画饼图；
- **为了通过检查删 validator**：覆盖只能改参数，不能删检查；
- **一个策略包打天下**：同一问题至少保留两个策略，避免“默认总是 Top-N”；
- **契约与测试脱节**：新增/修改契约必须同时加/改回归测试。
