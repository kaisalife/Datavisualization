# 验收与落地计划

## 1. 分阶段交付

### P0：可视化准备层的最小闭环

**目标**：让“脏数据画不出/画得差”的问题先被准确识别，并能用少量高价值策略修好；
MCP 在这一阶段就接入，而不是等所有规则成熟后才包装。

交付物：

- `service/data_ingestion/visual/models.py`：`VisualIntent` / `VisualSignal` /
  `ChartContract` / `PreparationPlan` / `PreparationResult`；
- `service/data_ingestion/visual/contracts.py`：加载 `configs/visualization_contracts.json`；
- `service/data_ingestion/visual/profile.py`：可视化画像与信号；
- `service/data_ingestion/visual/fitness.py`：按图表契约评估；
- `service/data_ingestion/visual/strategies.py`：问题 → 候选策略；
- `service/data_ingestion/visual/operations.py`：P0 操作；
- `service/data_ingestion/visual/plan.py`：组合、dry-run、确认；
- `service/data_ingestion/visual/variants.py`：变体落盘/读取；
- `configs/visualization_contracts.json`：Line / Bar / Pie / Histogram / Scatter 契约；
- `agent_tools/tool_visual_preparation.py`：5 个 MVP 工具；
- `skills/visual-data-preparation/SKILL.md`；
- `router._assemble_profile` / `series/splitter.py` 写入 `extra_semantics.visual` 摘要；
- `api/data-profile` 返回 `visual_summary`；
- 回归测试：`tests/test_visual_contracts.py`、`tests/test_visual_fitness.py`、
  `tests/test_visual_operations.py`、`tests/test_visual_mcp.py`。

P0 操作范围：

- `normalize_schema` / `coerce_numeric`：复用现有逻辑；
- `exclude_rows`：合计/小计/空行；
- `aggregate`：重复时间点、业务键重复；
- `top_n` + `other_bucket`：类别过多；
- `sort_rows`：时间/排名；
- 视图：`truncate_labels` / `label_rotation` / `axis_scale`（只写计划，不改数据）。

**完成标准**：

- 现有核心回归不退化；
- 对 8 类脏数据能给出正确的 `ready / needs_preparation / not_fit`：
  合并表头 Excel、图片抽表、PDF 抽表、长表、类别过多、重复时间点、合计行、含负值饼图；
- `dry-run` 不写 parquet，`commit` 生成新变体，旧版本仍可读；
- MCP 5 个工具能在真实规划会话中调用，不是只通过单测；
- 任一步失败都能回退原始版本，图表任务给出明确原因。

### P1：策略库、规划接入与反馈闭环

**目标**：让准备能力真正影响图表规划与生成，而不是“可用但不被使用”。

交付物：

- `strategies.py` 扩展：缺失策略、时间重采样、长转宽、单位拆列/换算（显式）、派生指标；
- `compare_preparations` / `validate_visual_data` / `explain_preparation` / `recommend_chart_options`；
- `agent_plan_stage` 工具池接入准备工具；
- `prompts/agent_planning_prompt.py` 增加 `preparation_id` 和“先评估再准备”规则；
- `chart_executor` 按 `preparation_id` 读取变体；
- `generation_validation` 将渲染后问题映射到准备信号；
- `api/chart_api` 接受 `preparation_plan` / `preparation_id` / `visual_intent`；
- 回归测试：`tests/test_visual_planning.py`、`tests/test_visual_feedback.py`、
  `tests/test_visual_variants.py`。

**完成标准**：

- 规划 agent 在 Pie/Bar/Line 场景会先看就绪度，而不是直接写代码；
- 有 2–4 个策略时能给出取舍，不默认选“丢数据最多”的方案；
- 用户确认后生成的变体，其图表 HTML 中的数据与变体 parquet 一致；
- `CHART_DATA_ALL_ZERO` / `CHART_DATA_EMPTY` 能给出可执行的准备建议；
- 没有确认 token 的破坏性操作被拒绝；
- 同一输入 + 同一策略 → 同一变体内容。

### P2：外部抽取器与前端

**目标**：在现有 reader 抽表失败/退化时提供可选增强；前端能查看就绪度、选择策略、对比前后。

交付物：

- `visual/adapters.py`：Docling / OCRFlux 适配（feature flag，默认关闭）；
- 预览页“可视化就绪度”面板：状态、信号、候选策略、影响行数；
- 准备前后对比：行数/列数/缺失/类别数/示例值；
- 用户可选择原始版本 / 准备版本 / 不同策略；
- 可选：领域契约通过 skill 扩展（高频、K 线、多序列、多模态）。

**完成标准**：

- 外部工具不可用/超时，自动回退现有 reader，任务不失败；
- 前端能明确显示“哪些是自动、哪些需要确认”；
- 真机跑通至少 1 个扫描 PDF + 1 个 docx 内嵌表格截图 → 准备 → 图表；
- 用户能回退到原始版本并重新出图。

## 3. 验收标准

### 3.1 可视化效果（最重要）

- **可出图率**：同一批脏数据，准备后图表成功率高于准备前；
- **可读性**：类别过多时自动 Top-N + 其他，或建议横向条形/分组，不出现 40 个扇区的饼图；
- **正确性**：饼图不含负值；时间序列按时间顺序；合计行不参与份额/对比；重复时间点已聚合；
- **一致性**：plan 的 `preparation_id`、变体 parquet、图表 HTML 三者数据一致；
- **可解释**：每张“改过数据”的图都能说明改了什么、为什么、影响多少行；
- **可回退**：用户能选择原始版本重新出图。

### 3.2 灵活性

- 同一问题至少有两种可执行策略（如类别多：Top-N / 分组 / 横向条形）；
- 阈值、图表上限、默认策略来自配置/契约，不在代码里散落；
- skill 可以覆盖领域策略，不需要改核心代码；
- 用户约束（`must_keep` / `must_exclude` / `max_points` / `allow_information_loss`）能影响策略；
- 新增图表类型只需加契约和少量操作，不需要改 MCP 协议。

### 3.3 安全性

- 原始文件、原始 series 不被覆盖；
- 路径只能落在当前会话目录；
- 不执行任意代码，不发起未授权网络请求；
- 日志不打印原始敏感值；
- SQL 仍走 `ensure_read_only()`；
- 破坏性操作无确认 token 时拒绝。

### 3.4 性能

- 1 万行 × 50 列的画像 + 5 个图表契约评估在 2 秒内完成（本机 CPU）；
- 10 万行以上采用采样画像 + 分块执行，避免一次性复制多份 DataFrame；
- dry-run 只做必要复制，预览采样；
- 变体数量有上限（例如每个 series 保留最近 8 个），过期清理；
- 外部抽取器有超时和回退，不拖垮整个任务。

## 4. 风险与待确认问题

| 问题 | 现状 | 建议 |
|---|---|---|
| 契约是否太死 | 图表要求因场景而异 | 契约可配置，skill 可覆盖；默认只覆盖常用图 |
| 策略是否太多 | 每个问题 2–4 个方案 | 限制数量，按“信息损失/改动大小”排序 |
| 谁来判断“重复” | 代码只能检测完全重复/业务键重复 | 默认聚合或报告；模糊重复只给候选 |
| 单位换算 | 列名/值里可能有 `万元`、`%`、`人` | 保留原单位；换算需用户确认 |
| 合计行 | 常见于中文报表 | 默认排除；用户可要求保留并标注 |
| 多表主表选择 | 一图多表/多 sheet | 先让用户/agent 确认主表，不硬拼 |
| 准备变体过多 | 每个策略一个版本 | 每 series 限制数量 + TTL；默认只保留用户选中的 |
| MCP 状态 | 进程重启后句柄失效 | 状态从 manifest 重建；token 绑定 dataset/series/plan |
| 外部工具许可证 | Docling MIT、OCRFlux Apache-2.0 | 引入前再次确认分发方式 |
| 与图表推荐重叠 | `chart_recommend` 已给建议 | 准备层只回答“能不能画/怎么准备”，不重复 plan 多样性逻辑 |

## 5. 建议的下一步

1. 先写 `models.py` + `contracts.py` + `configs/visualization_contracts.json`，把 Line/Bar/Pie 的契约跑通；
2. 写 `profile.py` / `fitness.py`，用现有 series 夹具验证 ready/needs/not_fit；
3. 写 `operations.py` 的 P0 五个操作，先只做 dry-run 和影响统计；
4. 接 `router._assemble_profile` 与 `/api/data-profile`，用真实脏数据看信号是否准确；
5. 再做 MCP 5 个工具和 skill，接一个真实规划路径；
6. 最后用 3–5 个真实脏数据案例校准策略和阈值，再考虑 P1/P2。
