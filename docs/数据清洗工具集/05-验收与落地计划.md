# 验收与落地计划

## 1. 分阶段交付

### P0：确定性清洗层（无新增重依赖）

**目标**：抽表后能自动处理低风险结构/值问题，并给出可读的质量报告；不改变现有图表主流程的成功率。

交付物：

- `service/data_ingestion/cleaning/models.py`：`CleaningIssue` / `CleaningAction` / `CleaningReport`；
- `service/data_ingestion/cleaning/rules.py`：规则注册表 + 检测函数；
- `service/data_ingestion/cleaning/profile.py`：质量检查；
- `service/data_ingestion/cleaning/apply.py`：安全规则执行；
- `service/data_ingestion/cleaning/report.py`：JSON 读写；
- `router._assemble_profile` 接入：生成 `cleaning_report`，默认不阻断；
- `api/data-profile` 返回 `cleaning_summary`；
- 回归测试：`tests/test_data_cleaning.py`。

P0 规则范围：

- 自动：列名空白/重复、数值文本、空值占位符、编码；
- 只报告：缺失、重复、异常、合计行、单位混用、时间缺口、常量列、高基数；
- 不做：填充、删除、单位换算、跨表合并。

**完成标准**：

- 现有核心回归不退化；
- 对 6 类真实文件（普通 CSV、GBK CSV、合并表头 Excel、图片抽表、PDF 抽表、docx 内嵌图）都能产出报告；
- 报告中的数字与 DataFrame 实际统计一致；
- 不因为清洗报告失败导致图表任务失败。

### P1：Skill + MCP

**目标**：agent 能在需要时加载清洗技能，并通过 MCP 工具执行 dry-run / commit，而不是临时写 pandas。

交付物：

- `skills/multimodal-data-cleaning/SKILL.md`；
- `service/skills/registry.py` 支持清洗能力的匹配（或独立 loader）；
- `agent_tools/tool_data_cleaning.py`：6 个 MVP 工具；
- `configs/default_config.json` 注册 `data_cleaning`；
- `api/chart_api` 接受 `cleaning_plan`（可选）；
- 回归测试：`tests/test_cleaning_mcp.py`、`tests/test_cleaning_skill.py`。

**完成标准**：

- agent 在“截图/合并表头/缺失严重”的请求下会先 profile，而不是直接画图；
- `apply_cleaning_plan(dry_run=true)` 不修改数据，返回 affected 统计；
- `dry_run=false` 后版本号递增，原始版本仍可访问；
- 破坏性动作（删行/填充）在未确认时被拒绝；
- MCP 工具不执行任意代码、不访问会话目录外路径。

### P2：外部抽取器与前端

**目标**：在现有 reader 抽表失败/退化时提供可选增强；前端能查看质量问题和清洗前后对比。

交付物：

- `cleaning/adapters.py`：Docling / OCRFlux 适配（feature flag，默认关闭）；
- 预览页“数据质量”面板：问题列表、严重级别、影响行数、建议；
- 清洗前后对比：行数/列数/缺失率/示例值；
- 可选：pandera schema 校验（仅当规则复杂到需要时）。

**完成标准**：

- 外部工具不可用/超时，自动回退现有 reader，任务不失败；
- 前端能明确显示“哪些是自动处理、哪些需要确认”；
- 用户可以选择使用原始版本或清洗版本；
- 真机跑通至少 1 个扫描 PDF + 1 个 docx 内嵌表格截图。

## 3. 验收标准

### 3.1 正确性

- 所有清洗动作都有 `before/after` 计数；
- 没有未声明的行/列丢失；
- 自动规则幂等；
- 同一输入 + 同一计划 → 同一输出（字节级或内容级）；
- 数值转换失败时整列回退，不做部分转换。

### 3.2 安全性

- 原始文件、原始表不被覆盖；
- 路径只能落在当前会话目录；
- 不执行任意代码，不发起未授权网络请求；
- 日志不打印原始敏感值；
- SQL 仍走 `ensure_read_only()`。

### 3.3 可用性

- 质量问题用中文、带列名和示例行号；
- `warn` 不阻断图表；`error` 阻断并说明原因；
- 用户能选择“使用原始数据”；
- 报告可在预览页打开/导出，不依赖 LLM。

### 3.4 性能

- 1 万行 × 50 列的基础检查在 2 秒内完成（本机 CPU）；
- 10 万行以上采用采样统计 + 分块清洗，避免一次性复制多份 DataFrame；
- 外部抽取器有超时和回退，不拖垮整个任务。

## 4. 风险与待确认问题

| 问题 | 现状 | 建议 |
|---|---|---|
| 清洗是否默认开启 | 建议默认只做安全规则 + 报告 | 破坏性操作必须显式确认 |
| 谁来判断“重复” | 代码只能检测完全重复/业务键重复 | 模糊重复只给候选，不自动合并 |
| 单位换算 | 列名/值里可能有 `万元`、`%`、`人` | 保留原单位；换算需用户确认 |
| 合计行 | 常见于中文报表 | 只提示，不自动删；图表计划应排除 |
| 多表主表选择 | 一图多表/多 sheet | 先让用户/agent 确认主表，不硬拼 |
| 清洗报告与分析报告 | 两者概念不同 | 字段分开：`cleaning_report_path` vs `report_path` |
| 技能注册 | 现有 registry 偏图表匹配 | 扩展 `capabilities` 或独立 loader，不硬编码 |
| 外部工具许可证 | Docling MIT、OCRFlux 需核实 | 引入前确认许可证与分发方式 |

## 5. 建议的下一步

1. 先实现 P0 的 `models.py` / `rules.py` / `profile.py` / `report.py`，只做检测与安全规则；
2. 把报告接到 `/api/data-profile`，用真实文件看输出，再决定阈值和前端展示；
3. 用 3–5 个真实脏数据案例（合并表头、缺失、合计行、单位混用、扫描件）校准规则；
4. 规则稳定后再做 MCP 和 skill，避免把不成熟的规则固化给 agent；
5. 最后再评估 Docling/OCRFlux，不要一开始就引入重依赖。
