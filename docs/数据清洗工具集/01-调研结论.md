# 调研结论：有没有现成的多模态数据清洗工具集？

## 1. 调研范围与方法

- 本地仓库：`skills/`、`agent_tools/`、`configs/default_config.json`、`service/data_ingestion/`、
  `service/pipeline/`、`tests/`；
- 本地现状：
  - `skills/` 只有图表场景技能（高频时序、K 线、多序列、多模态抽表），没有数据准备技能；
  - `agent_tools/` 只有 `run_code` MCP，没有可视化数据准备工具；
  - 数据接入层已有 reader、列名清洗、数值归一化、解析画像、series 拆分；
  - 图表层已有类型推荐、数据形态摘要、渲染后空数据检查。
- 外部检索：MCP 目录 / GitHub / 官方文档 / Skills 合集；
- 检索关键词：`data cleaning MCP`、`multimodal data cleaning`、`OCR table extraction MCP`、
  `Claude skill data cleaning`、`visualization data preparation`、`chart data validation`、
  `数据清洗 MCP`、`多模态 数据清洗`、`图表数据准备` 等；
- 判断标准不只看“能不能清洗”，而是看：
  1. 是否覆盖**图片 / PDF / Office 内嵌表格**与**表格结构归一化**；
  2. 是否理解**图表意图**，能按图表类型判断数据是否可画；
  3. 是否支持**多策略组合、dry-run、版本回退、来源追溯**；
  4. 是否适合本项目：Windows、本地优先、Python、中文报表、无 GPU、可与现有 pipeline 对接；
  5. 是否会把“清洗”变成不可解释的自动改数。

## 2. 结论

**没有找到一个可以直接替换本项目数据接入层、并且真正面向可视化的“多模态数据清洗”skill / MCP 工具集。**

现成项目大多只覆盖其中一段，而且有一个共同问题：**它们清洗的是表，不是图**。

- 文档解析工具负责“把图片/PDF 变成文本或表格”，但不判断表头是否正确、数值是否可解析、
  类别是否过多、负值能否画饼图、时间轴是否连续；
- 通用表格清洗 MCP 负责“对 DataFrame 做 pandas 操作”，但默认输入已经是干净的表，
  不理解扫描件、合并表头、跨页续表，更不知道当前用户要画什么图；
- Agent Skills 负责“告诉模型怎么做”，但多数是通用 pandas/numpy 步骤，
  缺少面向中文报表的确定性规则、图表契约和变更审计。

因此推荐的路线是：

```text
现有 reader 负责多模态接入
  + 项目内新增“可视化准备层”（图表契约 + 信号 + 可组合策略 + 变体）
  + MCP 作为薄适配器暴露给 agent
  + Docling / OCRFlux 只在抽取失败时作为可选适配器
```

## 3. 为什么通用清洗 MCP 对可视化不够

### 3.1 没有图表意图，清洗目标就是错的

同一份数据在不同图表下需要不同处理：

| 数据现象 | 画折线图 | 画饼图 | 画柱状图 |
|---|---|---|---|
| 某个月缺失 | 可以保留断点，观察缺口 | 不能把缺失类别当作 0 份额 | 可以排除该类别或标注缺失 |
| 同一时间点两行 | 应聚合，否则折线来回折 | 通常应聚合 | 应聚合或拆分 |
| 类别有 40 个 | 可以画多线但不可读，需 Top-N/分组 | 饼图不可用 | Top 10 + 其他，或横向条形 |
| 含负值 | 可画，需零基线 | 不可用（份额无意义） | 可画，需处理正负对比 |
| 两个指标量级差 1000 倍 | 双轴或分图 | 不适用 | 双轴或分图 |
| 有“合计”行 | 会形成虚假尖峰 | 会重复计算份额 | 会压扁其他类别 |

通用 MCP 只能给出“有缺失 / 有重复 / 有异常”，不能回答“这张图还能不能画、应该怎么准备”。

### 3.2 规则是全局的，策略是单一的

通用工具通常提供：

- `dedupe_rows`：删重复行；
- `handle_missing`：填均值/中位数/前向填充；
- `detect_outliers` + 删除；
- `normalize`：统一单位/编码。

这些操作对可视化经常是**错误默认值**：

- 重复行可能是多批次真实记录，直接删会改变总量；图表更需要“按业务键聚合”；
- 缺失值填 0 会在折线图上制造虚假的“归零”，比保留缺口更危险；
- 删除异常值会让用户看不到真实尖峰；
- 统一单位可能改变量纲，且没有在图上标注。

可视化准备需要的是**多个可选策略 + 影响预览**，而不是一个全局开关。

### 3.3 不可预览、不可回退、不可解释

很多 MCP 工具直接返回“清洗后的文件”，中间过程不可见：

- 不知道改了哪些行、哪些列；
- 不知道删除/填充是否影响当前图表；
- 不能对比“保留缺口”和“补齐时间轴”两种方案；
- 出错后只能重跑，不能回到原始版本。

本项目的图表任务需要可复现和可审计，必须把每次准备写成结构化的变更清单。

### 3.4 与图表校验脱节

现有 `chart_data_check` 已经能在渲染后发现：

- 没有 series；
- 所有数据点为空；
- 所有数值为 0；
- 实际 series 类型与 plan 不符。

但通用清洗 MCP 不知道这些信号，也不会根据“空图/全 0/类型不符”反推数据准备问题。
真正有用的闭环应该是：

```text
图表检查发现问题 → 映射为可视化信号 → 提出准备策略 → 重新生成
```

### 3.5 多模态来源没有进入决策

图片/PDF 抽出来的表，常见问题不是“缺失值”，而是：

- 表头被识别成数据；
- 单位在表头里，数值列没有单位；
- 合并单元格导致类别只出现一次；
- 跨页续表导致重复表头；
- 一图多表导致主表选错。

这些需要**来源感知**的准备策略，而不是通用 DataFrame 清洗。现有 `source_kind` / `source_path`
已经进入 series 的 `extra_semantics`，应该继续用于技能和策略选择，而不是在图表代码里写特判。

## 5. 为什么不让 LLM 直接“清洗”

- 同一输入不一定得到同一输出，无法解释每一行为什么被改；
- 缺失值填 0、按均值填充、删除“异常值”在业务上可能是错误操作；
- 图表任务需要的是**可复现的 series 变体**，不是一段看起来合理的叙述；
- LLM 适合做策略选择、歧义提问和解释，不适合生成或补造数据值；
- 项目已有确定性 reader、normalizer、profiler 和 splitter，正确做法是补一层确定性准备能力。

## 6. 推荐路线

### P0：可视化准备层的最小闭环

- 新增 `service/data_ingestion/visual/`；
- 建立**图表契约注册表**（Line / Bar / Pie / Histogram / Scatter / Boxplot / Treemap 等）；
- 在 series 落盘时计算**可视化信号**与**就绪度摘要**；
- 实现 4 个高价值操作：排除合计行、聚合重复时间点、Top-N + 其他、排序；
- 支持 dry-run、变体落盘、变更清单；
- MCP 只做 5 个工具：列出 series、评估、建议、预览、应用；
- 先接一个真实图表路径，验证“脏数据 → 准备 → 出图”确实改善。

### P1：策略库与反馈闭环

- 扩充操作：长转宽、时间重采样、缺失策略、单位拆列/换算（显式）、派生指标、视图变换（对数轴/标签截断）；
- 支持多方案对比（`compare_preparations`）；
- 规划 prompt 注入“就绪度 + 推荐策略”，但不把全部细节塞进上下文；
- `chart_data_check` 的错误反哺准备层；
- skill 提供领域策略（高频时序、K 线、多序列、多模态抽表）。

### P2：外部抽取器与前端

- Docling / OCRFlux 作为可选抽取适配器，失败自动回退；
- 预览页展示“就绪度、问题、候选策略、准备前后差异”；
- 用户可以选择原始版本 / 准备版本 / 不同策略；
- 领域契约通过 skill 扩展，不进入核心代码。

## 7. 关键取舍

| 问题 | 选择 | 理由 |
|---|---|---|
| 是否引入通用清洗 MCP | 否 | 不理解图表意图，默认操作经常破坏可视化语义 |
| 是否自动填充缺失值 | 否，默认保留缺口/报告 | 填充可能制造虚假趋势 |
| 是否自动删除重复行 | 否，默认聚合或报告 | 重复可能是真实多批次记录 |
| 是否自动剔除异常值 | 否，默认保留/视图层处理 | 异常值可能是真实尖峰 |
| 是否自动换算单位 | 否，除非用户明确 | 量纲错误比不换算更危险 |
| 是否让 LLM 生成准备计划 | 可以建议 | 但必须转成结构化操作，dry-run 后执行 |
| 是否覆盖原表 | 否 | 变体版本化，支持回退和对比 |
| 是否把规则写死在代码里 | 否 | 契约、阈值、领域策略可配置 |
