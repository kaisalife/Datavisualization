# 工具清单

本清单按“对可视化是否真的有用”分三层：

1. **已有能力**：项目里已经实现、经过测试，直接复用；
2. **待补能力**：现有链路缺少、但会直接影响图表可出图性和可读性的能力；
3. **外部候选**：只补抽取或领域能力，不作为核心清洗引擎。

> 选择工具的唯一标准：能否让真实脏数据更容易产出**正确、可读、可解释**的图表。
> 单纯“把表洗干净”但和图无关的能力，不进主链路。

## 二、待补能力（本目录设计的重点）

这些能力不是“再写一个 pandas 工具”，而是把图表需求变成可执行、可验证的准备过程。

| 能力 | 作用 | 关键点 |
|---|---|---|
| 图表契约注册表 | 定义每种图对数据的要求（轴、指标、基数、负值、点数、缺失策略） | 可配置、可扩展，不在代码里散落阈值 |
| 可视化画像 | 在 series 上计算时间性、基数、单位、缺失、重复、极值、标签长度等 | 只读，随 manifest 持久化 |
| 就绪度评估 | 对“候选 series × 图表类型”给出 `ready / needs_preparation / not_fit` | 必须说明 blocker 和可行动作 |
| 准备策略生成 | 对同一问题给出 2–4 个策略（保留缺口/Top-N/聚合/拆图） | 带取舍、影响行数、是否需要确认 |
| 操作执行器 | 组合执行结构/值/聚合/视图操作 | dry-run、幂等、可回退 |
| 变体管理 | 每次准备生成新变体，原始版本只读 | 版本号、来源、变更清单 |
| 反馈适配器 | 把空图/全 0/类型偏离映射回准备策略 | 形成“生成失败 → 修正数据准备 → 重试”的闭环 |
| 准备 skill | 告诉 agent 何时评估、如何选策略、何时问用户 | 不把规则写进主 prompt |

### 为什么这些能力必须独立于 MCP

- MCP 进程不适合保存整张 DataFrame，也不适合承担所有计算；
- 同一个准备能力要同时被 API、图表编排、MCP 和测试调用；
- 把核心放在 `service/data_ingestion/visual/`，MCP 只做参数校验和状态转发，才能保证行为一致。

## 四、依赖策略

### P0：不新增依赖

- 使用已有 `pandas`、`numpy`、`pyarrow`、`openpyxl`、`xlrd`、`unstructured`、`pypdfium2`、`pillow`；
- 图表契约用 Python dataclass + JSON 配置，不引入 schema 框架；
- 变体落盘继续用 parquet + manifest，不引入数据库；
- 预览用现有 JSON/HTML 能力，不引入前端图表库。

### P1：按需可选

如果策略复杂到需要更强约束，再考虑：

```toml
[project.optional-dependencies]
visual-prep = [
    "pandera>=0.20",   # 可选：复杂契约校验
]
```

> 不要直接改 `dependencies`。新增依赖前先确认真实需求、许可证、Windows 兼容性和安装体积。

### P2：外部抽取器

- Docling / OCRFlux 作为**可选 extra** 或独立进程/容器，不进入默认安装；
- 通过环境变量或配置开关启用，例如 `VISUAL_PREP_DOCLING=1`；
- 失败时回退到现有 `MultimodalReader`，不能因为外部工具不可用导致整条链路失败。

## 五、明确不做的事

- 不把通用清洗 MCP 当成核心依赖；
- 不用 LLM 直接“清洗”整张表并覆盖原数据；
- 不自动把缺失值填 0 / 均值 / 前向填充；
- 不自动删除重复行或异常值；
- 不自动把 `万元` 转成 `元`、把百分比转成小数，除非用户明确要求；
- 不把多个来源不同的表按列名相似度自动合并；
- 不为了“看起来干净”而重命名所有列，列名保真是多模态抽表的基本要求；
- 不额外生成独立文档；这里只产出结构化的准备清单和变体。
