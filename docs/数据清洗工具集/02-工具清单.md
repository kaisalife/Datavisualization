# 工具清单

本清单按“对可视化是否真的有用”分三层：

1. **已有能力**：项目里已经实现、经过测试，直接复用；
2. **待补能力**：现有链路缺少、但会直接影响图表可出图性和可读性的能力；
3. **外部候选**：只补抽取或领域能力，不作为核心清洗引擎。

> 选择工具的唯一标准：能否让真实脏数据更容易产出**正确、可读、可解释**的图表。
> 单纯“把表洗干净”但和图无关的能力，不进主链路。

## 二、待补能力（本目录设计的重点）

只缺一件事：**在 series 之上支持声明式的派生数据视图（DataView）**。
能力拆成四块，全部在 `service/data_view/`：

| 能力 | 作用 | 关键点 |
|---|---|---|
| ViewSpec 与 hash | 声明一条只读 SQL 或插件引用，`view_id = hash(source + spec + engine_version)` | spec 可序列化进 manifest，可审计 |
| 执行器 | SQLite（内存）执行 SQL、插件执行、行数阈值、结构化错误码 | 复用 `sql_safety.ensure_read_only` |
| 缓存 | `view_id -> parquet` 落盘/命中；失败绝不缓存 | 数据 hash 变更自动 miss |
| 插件注册 | `plugins/data_view/<name>.py` 纯函数 + `OUTPUT_SCHEMA` 声明 | 新能力只加文件，不改核心 |

MCP 只暴露 `describe_dataset` / `run_view` 两个工具（设计见 04）；不设图表契约、
就绪度、多策略对比——判图能力保留在生成代码与 `chart_data_check`，职责不迁移。

## 四、依赖策略

### P0：不新增依赖

- 核心执行器用**内置 `sqlite3`**（零新增依赖，Windows 自带）；
- 缓存沿用 parquet + manifest（`pyarrow` 已是硬依赖）；
- ViewSpec 校验用 dataclass + 手写校验，不引入 schema 框架；
- MCP 用已有 `fastmcp 3.4.x`（见 AGENTS.md 依赖约束，勿升级）。

### P1/P2：按需可选

- 大表场景执行引擎可换 DuckDB（可选 extra，不进默认 `dependencies`；装包走清华镜像）；
- 外部抽取器（Docling / OCRFlux）与 view 层无关，属于接入层可选增强：
  P2 首选适配器、默认关闭、失败回退现有 reader。

## 五、明确不做的事

- 不把通用清洗 MCP 当成核心依赖；
- 不用 LLM 直接“清洗”整张表并覆盖原数据；
- 不自动把缺失值填 0 / 均值 / 前向填充；
- 不自动删除重复行或异常值；
- 不自动把 `万元` 转成 `元`、把百分比转成小数，除非用户明确要求；
- 不把多个来源不同的表按列名相似度自动合并；
- 不为了“看起来干净”而重命名所有列，列名保真是多模态抽表的基本要求；
- 不额外生成独立文档；变换的记录就是 view manifest（spec + lineage），可读可审计。
