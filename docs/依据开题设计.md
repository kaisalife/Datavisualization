## 1. 项目定义

### 1.1 项目名称与定位

- 项目名称：**基于 LangChain 的数据可视化智能体的设计与实现**。
- 项目类型：应用型、非立项。
- 产品形态：面向 Windows 10/11 的**轻量化桌面应用**，前端使用 WinUI，后端使用 Python。
- 核心定位：把“数据清洗 → 数据分析 → 数据可视化”串成一条自然语言驱动的智能体工作流，让普通用户不必掌握编程或专业可视化工具，也能完成数据分析与图表生成。

### 1.2 需要解决的核心问题

1. **可视化编程门槛高**：传统工具要求用户把分析意图翻译成代码、脚本或复杂的界面操作，学习和使用成本高。
2. **特定问题需要重新设计流程**：数据源、数据形态或分析目标变化后，用户往往要重新组织数据处理和绘图步骤。
3. **智能生成链路不稳定**：需要重点解决数据结构识别偏差、图表类型匹配不合理、生成代码报错等问题。
4. **多模态数据难以直接分析**：图片、PDF、Office 文档等非结构化内容需要先转换为可分析的二维表。

### 1.3 总体目标

系统要完成从“用户自然语言提示词 + 多模态数据输入”到“可交互图表结果”的端到端闭环，具体包括：

- 支持常见数据格式和多模态数据的读取、清洗与结构识别；
- 支持用户用自然语言表达分析目标，系统自动完成意图解析、图表规划和图表生成；
- 支持折线图、柱状图、饼图、散点图等常见图表，并能根据数据形态匹配合适类型；
- 生成交互式 HTML 图表，支持放大、悬停查看等基础交互；
- 图表自动保存到指定目录，并按数据文件名分类管理；
- 通过 RAG 检索可视化代码示例，降低大模型生成图表代码的错误率；
- 采用中心 Agent + Skill 的分层架构，模块可独立扩展、升级；
- 记录完整执行日志，支持过程追溯与问题调试；
- 保持桌面端操作简单、交互友好，普通用户无需专业技术背景即可上手。

### 1.4 目标用户与使用场景

**目标用户**

- 不具备编程能力的普通办公用户；
- 需要完成课程作业、数据分析报告的学生；
- 需要快速探索数据的小型科研人员；
- 需要重复制作图表的业务人员。

**典型场景**

- 日常办公：把 Excel/CSV 销售数据转成趋势图、对比图、占比图；
- 学习作业：上传课程数据，用自然语言描述图表要求并导出交互式 HTML；
- 小型科研：接入数据库或实验数据，快速完成多轮探索性可视化；
- 多模态资料整理：从表格截图、扫描 PDF、带表格截图的 Office 文档中抽取数据后绘图。

### 1.5 交付形态

- **必须**：Windows 10/11 可运行的桌面应用，前端基于 WinUI。
- **必须**：后端以 Python 实现，通过 LangChain 编排大模型、RAG、数据处理和代码执行。
- **必须**：图表结果为独立 HTML 文件，可在应用内预览，也可直接用浏览器打开。
- **应该**：应用内提供工作区，用户可以选择/打开工作文件夹并管理其中的数据文件。
- **可**：后续扩展为安装包或单文件分发，但开题报告未规定具体打包方式。

## 2. 总体业务流程

### 2.1 端到端流程

1. 用户打开或选择工作区文件夹，选择数据文件、数据库连接或多模态资料。
2. 用户用自然语言输入分析目标，例如“按月份展示销售额趋势，并标出最高月份”。
3. **DataPreviewSkill（数据预览）**读取数据，完成结构识别、数据清洗和预览，输出统一的数据摘要。
4. 中心 Agent 把用户需求、数据摘要、对话历史和检索结果交给 **ChartPlanSkill（图表计划）**。
5. ChartPlanSkill 解析意图，确定分析角度、图表类型、指标、维度、数据变换和多图组合，输出结构化计划。
6. **ChartGenerateSkill（图表生成）**根据计划生成 Pyecharts 代码，通过 MCP 服务的 Code 工具执行代码，渲染交互式 HTML。
7. 图表按数据文件名分类保存，返回前端预览；执行过程、提示词、代码和错误写入日志。
8. 用户通过多轮对话继续修改，例如“改成柱状图”“只看前五名”“增加标题”，系统结合上下文重新规划或生成。

### 2.3 LangChain 调用链

开题报告要求的基本链路为：

1. 接收用户输入；
2. 把用户输入、系统角色、历史信息、数据摘要和检索结果填入提示词模板；
3. 智能体根据提示词和可用工具进行决策与规划；
4. 调用大语言模型生成原始输出；
5. 上下文记忆模块在调用前后读写对话历史，保证多轮连贯；
6. 对模型输出做后处理，返回自然语言聊天消息或图表结果。

## 3. 功能需求

### 3.1 数据接入

| 编号 | 需求 | 说明与验收要点 |
|---|---|---|
| FR-01 | **必须**支持 CSV、Excel 文件 | 能读取常见 CSV 和 Excel 文件；识别表头、列类型和行数据；Excel 支持一个文件中的多个工作表，不能只读第一页。 |
| FR-02 | **必须**支持数据库数据源 | 用户能配置数据库连接信息并读取表或查询结果；数据库类型至少覆盖一种常见关系型数据库，具体方言在实现阶段确定。 |
| FR-03 | **必须**支持“代码文档”等文件 | 开题报告明确要求支持代码文档；实现时需定义可解析的代码/文档格式，并提取其中可表格化的数据。 |
| FR-04 | **必须**支持多模态数据输入 | 能处理图片、扫描件/PDF、带表格截图的 Office 文档等非结构化资料；具体支持格式和页数上限在实现阶段确定。 |
| FR-05 | **必须**支持工作区文件选择 | 用户能打开/选择工作文件夹，在工作区文件管理器中浏览并选择数据文件。 |
| FR-06 | **必须**提供明确的接入错误提示 | 文件损坏、格式不支持、数据库连接失败、无有效表格、模型不可用等情况不能静默失败；需要返回可读原因和修复建议。 |
| FR-07 | **应该**保留原始数据 | 清洗和转换不能覆盖用户原始文件；预览和导出应能核对清洗前后的差异。 |

### 3.2 DataPreviewSkill（数据预览与清洗）

DataPreviewSkill 对应“数据清洗”阶段，是后续图表计划的事实基础。

| 编号 | 需求 | 说明与验收要点 |
|---|---|---|
| FR-08 | **必须**识别数据结构 | 自动识别表头、列名、字段类型、类别列、数值列、时间列、缺失值、重复列等；对表头合并、标题行、空行、多工作表等常见情况做容错。 |
| FR-09 | **必须**完成基础数据清洗 | 处理缺失值、空值占位符、重复列名、数值文本（千分位、百分号、货币符号等）、日期/时间格式和不合法类型；清洗规则要可解释、可复现。 |
| FR-10 | **必须**输出可核对的数据预览 | 展示列名、数据类型、前若干行、行列数、缺失情况、识别出的维度/指标/时间字段等；让用户在生成图表前确认数据是否读取正确。 |
| FR-11 | **必须**为多模态数据提供清洗方案 | 图片/PDF/Office 内嵌表格等先转换为二维表，再进入同一套预览、清洗和分析流程；抽取失败时要给出视觉模型、OCR 或文字层解析的具体原因。 |
| FR-12 | **必须**处理多表场景 | 一个文件或一份资料可能包含多张表；系统要能识别主表和相关表，至少保证用户可以选择或确认用于绘图的数据表。 |
| FR-13 | **必须**输出统一数据契约 | 预览结果要能为后续 ChartPlanSkill 和 ChartGenerateSkill 提供稳定的数据结构，包括表名、列名、类型、样例值、行数、指标/维度信息和数据质量提示。 |
| FR-14 | **应该**避免臆造数据 | 多模态抽取或表格识别不确定时，不能补全不存在的列名或数值；应保留原值、标注不确定项，或提示用户核对。 |

### 3.3 ChartPlanSkill（图表计划）

ChartPlanSkill 对应“数据分析”阶段，负责把自然语言需求翻译成可执行的图表计划。

| 编号 | 需求 | 说明与验收要点 |
|---|---|---|
| FR-15 | **必须**解析自然语言分析意图 | 从用户提示词中提取分析对象、时间范围、维度、指标、聚合方式、筛选条件、排序、图表标题、图表类型和图表数量等要求。 |
| FR-16 | **必须**匹配合理图表类型 | 至少支持折线图、柱状图、饼图、散点图；根据数据形态和分析角度选择类型，例如时间序列优先趋势图、类别对比优先柱状图、构成关系优先饼图、两个数值指标关系优先散点图。 |
| FR-17 | **必须**输出结构化图表计划 | 每个计划至少包含计划标识、图表类型、标题、使用的数据表/字段、x 轴、y 轴、系列、聚合或变换说明、排序/筛选、布局和多图关系。 |
| FR-18 | **必须**支持多图组合 | 当数据支持多个分析角度时，可以规划多张图；同一数据源、同一指标不能无意义重复出图；用户明确要求“画两个图”时，数量是硬上限。 |
| FR-19 | **必须**支持用户显式控制 | 用户明确指定图表类型时，以用户要求为准；用户指定标题、排序、Top N、筛选条件、颜色或布局时，计划应保留这些约束。 |
| FR-20 | **必须**处理歧义 | 用户需求不完整或存在多种合理解释时，应优先选择合理默认值并说明；无法安全推断时向用户追问，不能静默生成错误图表。 |
| FR-21 | **必须**做计划校验 | 生成代码前校验字段是否存在、类型是否可用、x/y 是否匹配、多图是否重复；明显不匹配的计划要修正或拒绝，不能直接把错误计划交给代码生成。 |
| FR-22 | **应该**保证图表可读性 | 中文标题、轴名称、单位、图例、数据标签、排序和配色要清晰；类别过多时做 Top N、旋转标签或隐藏拥挤标签，避免标签重叠和图形不可读。 |
| FR-23 | **应该**利用数据形态信息 | 规划时使用时间点数量、指标数量、类别数量、是否非负等数据形态信息，而不是只凭用户措辞或模型偏好决定图表类型。 |

### 3.4 ChartGenerateSkill（图表生成与执行）

ChartGenerateSkill 对应“数据可视化”阶段，负责把计划转成可运行代码和最终图表。

| 编号 | 需求 | 说明与验收要点 |
|---|---|---|
| FR-24 | **必须**使用 Pyecharts 生成图表 | 生成 Python 代码调用 Pyecharts 完成绘图；图表类型覆盖折线图、柱状图、饼图、散点图及计划中确定的其他类型。 |
| FR-25 | **必须**通过 MCP 服务的 Code 工具执行 | 生成代码不能只在后端进程中直接执行；按开题报告要求，由中心 Agent 调用 MCP 服务的 Code 工具完成代码执行并返回图表结果。 |
| FR-26 | **必须**生成交互式 HTML | 图表输出为独立 HTML；支持图表放大、数据悬停查看等基础交互，保留图例、tooltip 等可用交互能力。 |
| FR-27 | **必须**自动保存并分类 | 图表自动保存到指定目录，按数据文件名分类管理；文件名或目录要能避免同名任务互相覆盖，并便于用户定位结果。 |
| FR-28 | **必须**处理代码执行失败 | 代码报错时捕获异常，保留错误信息、失败代码和必要上下文；至少支持一次自动修复/重试，最终失败要返回明确错误，不能静默吞掉。 |
| FR-29 | **必须**支持多图任务 | 一个用户请求包含多个计划时，分别生成图表并返回全部结果；单张图失败不应导致其他已成功图表丢失。 |
| FR-30 | **必须**保证生成结果可追溯 | 保存图表计划、生成代码、执行结果和错误信息，便于复现、调试和后续修改。 |
| FR-31 | **应该**避免生成代码重复读取数据 | 数据读取由框架统一提供或注入，生成代码聚焦数据变换和绘图，减少重复读取、路径泄露和列名不一致。 |
| FR-32 | **应该**达到代码生成成功率目标 | 在约定的测试集和正常模型服务条件下，图表代码生成并成功渲染的比例不低于 90%。 |

### 3.5 RAG 向量检索

| 编号 | 需求 | 说明与验收要点 |
|---|---|---|
| FR-33 | **必须**建立本地可视化知识库 | 收录各类可视化代码示例、Pyecharts 用法和常见图表实现，作为大模型生成代码的参考。 |
| FR-34 | **必须**使用 Qwen Embedding 0.6B | 用 Qwen Embedding 0.6B 生成文档向量；模型和向量库均支持本地运行。 |
| FR-35 | **必须**使用 Chroma 向量数据库 | 用 Chroma 持久化向量和元数据，支持语义检索。 |
| FR-36 | **必须**按用户需求和图表类型检索 | 检索查询要结合用户意图与计划中的图表类型，返回相关示例并注入生成提示词，不能用无关文档干扰模型。 |
| FR-37 | **必须**处理检索失败 | 没有命中、向量库不可用或 embedding 失败时，图表生成仍应能继续（退化为无参考示例），并记录原因。 |
| FR-38 | **必须**支持知识库维护 | 能新增、更新、删除知识文档并重建或增量更新索引；知识库更新后检索结果应同步变化。 |
| FR-39 | **应该**控制检索质量 | 对检索结果做数量限制和相关性过滤，避免把过长、重复或低相关文档全部塞进提示词。 |

### 3.6 大语言模型适配与自然语言交互

| 编号 | 需求 | 说明与验收要点 |
|---|---|---|
| FR-40 | **必须**接入 OpenAI 兼容 API | 支持 DeepSeek、GLM 等 OpenAI 兼容大语言模型；模型服务地址、API Key、模型名称可配置。 |
| FR-41 | **必须**使用 ChatPromptTemplate | 用 LangChain 的 ChatPromptTemplate 管理系统角色、用户输入、历史信息、数据摘要和 RAG 参考文档。 |
| FR-42 | **必须**支持模型切换 | 更换模型或服务地址不需要改业务代码；前端模型设置组件能保存并生效。 |
| FR-43 | **必须**对模型输出做后处理 | 清理 Markdown 代码围栏、解析结构化计划、校验代码语法和必要字段，不能把模型原始输出直接当成可执行结果。 |
| FR-44 | **必须**处理模型异常 | 超时、限流、鉴权失败、输出截断、返回格式错误等情况要有重试或明确错误提示，不能导致应用崩溃。 |
| FR-45 | **应该**记录模型调用信息 | 记录模型名称、耗时、token 消耗和错误类型，便于性能评估与成本控制。 |

### 3.7 上下文记忆与多轮对话

| 编号 | 需求 | 说明与验收要点 |
|---|---|---|
| FR-46 | **必须**支持多轮自然语言交互 | 用户可以在上一轮结果基础上继续修改，例如“改成柱状图”“只看前五名”“把标题改一下”。 |
| FR-47 | **必须**实现三层记忆模型 | 借鉴 Claude Code 的三层记忆思路：短期记忆使用消息队列；中期记忆使用结构化总结与上下文压缩；长期记忆使用文件存储。 |
| FR-48 | **必须**控制上下文长度 | 对话过长时通过摘要、压缩和只保留必要信息控制 token；不能因为历史过长导致模型请求失败或关键约束丢失。 |
| FR-49 | **必须**支持会话持久化 | 长期记忆落盘，应用重启后能恢复必要的会话信息；用户可以新建、清空或切换会话。 |
| FR-50 | **应该**区分不同任务上下文 | 不同数据文件或不同分析任务的对话不能随意混在一起，避免上一轮字段或图表要求污染当前任务。 |

### 3.8 中心 Agent 与 Skill 协同

| 编号 | 需求 | 说明与验收要点 |
|---|---|---|
| FR-51 | **必须**采用中心 Agent + Skill 分层架构 | 中心 Agent 负责理解任务、调度 Skill、调用工具和汇总结果；DataPreviewSkill、ChartPlanSkill、ChartGenerateSkill 各自负责一个阶段。 |
| FR-52 | **必须**定义标准 Skill 契约 | 每个 Skill 有明确输入、输出和错误格式；Skill 之间通过结构化数据传递，不依赖隐式全局状态。 |
| FR-53 | **必须**支持独立调用 | 三个 Skill 能被单独测试和调用，便于定位问题、替换实现和后续扩展。 |
| FR-54 | **必须**支持工具调用 | 中心 Agent 能调用 MCP Code 工具以及其他必要工具；工具调用参数和结果要可记录、可追踪。 |
| FR-55 | **必须**做好失败隔离 | 单个 Skill 或工具失败时，其他已完成阶段和已生成图表不能被破坏；系统要能回退到可理解的错误状态。 |
| FR-56 | **应该**便于扩展新 Skill | 新增数据源、图表类型或分析方法时，不需要重写中心 Agent 的整体流程。 |

### 3.9 WinUI 桌面端

| 编号 | 需求 | 说明与验收要点 |
|---|---|---|
| FR-57 | **必须**使用 WinUI 开发前端 | 桌面端基于 WinUI；整体为轻量化桌面应用，不要求用户使用命令行。 |
| FR-58 | **必须**提供工作区与文件管理器 | 用户能选择/打开工作文件夹，在工作区中浏览文件、选择数据文件，并能看到当前工作目录。 |
| FR-59 | **必须**提供自然语言输入框 | 用户输入分析需求并提交；界面要显示任务状态、执行进度、成功结果或错误信息。 |
| FR-60 | **必须**提供模型设置组件 | 可配置模型服务地址、API Key、模型名称等参数；配置应能保存并在后续任务中复用。 |
| FR-61 | **必须**提供代码编辑器 | 能查看生成的 Python 代码；应该允许用户编辑代码，并明确编辑后是否重新执行。 |
| FR-62 | **必须**提供文本阅读器 | 能查看数据预览、日志、文本结果或其他长文本内容。 |
| FR-63 | **必须**提供 HTML 图表预览 | 在应用内展示生成的交互式 HTML 图表，支持放大和悬停查看；不能只返回文件路径。 |

| FR-65 | **应该**做到低学习成本 | 主流程不超过“选数据、写需求、点生成、看结果”几个步骤；错误提示使用普通用户能理解的语言。 |
| FR-66 | **可**支持拖拽文件、最近任务、任务取消等增强交互 | 这些不是开题报告的硬性要求，但可提升桌面端体验。 |

### 3.10 日志、配置与安全

| 编号 | 需求 | 说明与验收要点 |
|---|---|---|
| FR-67 | **必须**使用 Python logging 记录日志 | 使用 Python 标准库 logging，将执行过程、提示词、模型输出、代码、错误和耗时写入日志文件。 |
| FR-68 | **必须**支持过程追溯 | 每次任务有可关联的任务标识；能从日志定位到数据接入、规划、检索、代码生成、执行和落盘各阶段。 |
| FR-69 | **必须**保护敏感配置 | API Key、数据库密码等不能写入仓库、日志或可公开的图表文件；前端配置应保存在本地受控位置。 |
| FR-70 | **必须**限制代码执行风险 | MCP Code 工具执行生成代码时要有超时、异常隔离和必要的资源限制；失败不能拖垮主进程。 |

## 4. 非功能需求

| 编号 | 需求 | 验收口径 |
|---|---|---|
| NFR-01 | **性能：单次任务响应时间 ≤ 120 秒** | 从用户提交任务到图表 HTML 可预览，单个数据源、正常模型服务条件下测量；不含首次下载模型、首次建向量库等一次性准备时间。 |
| NFR-02 | **成本：单份任务 token 消耗 ≤ 0.3M** | 统计单次图表任务中所有大模型调用的输入、输出及推理 token 总量；超出时应能定位到具体阶段。 |
| NFR-03 | **代码生成成功率 ≥ 90%** | 在约定测试集上，生成代码能执行并产出包含有效图表和正确数据字段的 HTML，不需要人工改代码；失败需有日志和原因。 |
| NFR-04 | **兼容 Windows 10/11** | 在 Windows 10 和 Windows 11 上能安装/启动、打开工作区、完成一次完整图表生成；界面和文件路径处理不能依赖单一系统版本。 |
| NFR-05 | **易用性** | 普通用户无需编程背景即可完成主流程；关键操作有明确按钮、状态和错误提示。 |
| NFR-06 | **稳定性** | 单个文件、单次模型错误、单张图失败不能导致整个应用崩溃；任务失败后可继续提交新任务。 |
| NFR-07 | **可维护性** | 中心 Agent、Skill、数据接入、RAG、代码执行、前端分层清晰；模块可独立测试和替换。 |
| NFR-08 | **可扩展性** | 增加数据格式、图表类型、模型服务或知识库文档时，不需要重写整体架构。 |
| NFR-09 | **可观测性** | 关键阶段有日志、耗时和错误记录；能回答“任务卡在哪一步、为什么失败、消耗多少 token”。 |
| NFR-10 | **本地知识库能力** | RAG 的 embedding 和 Chroma 向量库可在本地运行，不依赖云端向量服务。 |
| NFR-11 | **安全性** | 满足敏感信息保护、代码执行隔离、数据库只读、路径校验等基本安全要求，并纳入测试。 |
| NFR-12 | **可测试性** | 数据处理、图表规划、图表生成、RAG 检索和前端主流程都能在不调用真实大模型的情况下做回归测试；真实模型测试单独标记。 |

## 5. 系统设计与技术约束

### 5.1 分层职责

| 层次 | 主要职责 | 关键实现 |
|---|---|---|
| 表现层 | 工作区、文件管理、输入、设置、代码/文本查看、HTML 预览 | WinUI |
| 交互编排层 | 提示词组织、Agent 决策、工具调用、上下文记忆 | LangChain、ChatPromptTemplate |
| Skill 层 | 数据预览、图表计划、图表生成 | DataPreviewSkill、ChartPlanSkill、ChartGenerateSkill |
| 数据能力层 | 文件/数据库/多模态读取、清洗、结构分析 | Pandas、文件读取器、多模态抽取 |
| 知识能力层 | 可视化代码示例检索 | Qwen Embedding 0.6B、Chroma |
| 执行层 | 生成代码执行、HTML 落盘、错误回传 | MCP Code 工具、Pyecharts |
| 支撑层 | 配置、日志、异常、测试 | Python logging、Git、依赖管理 |

### 5.2 Skill 输入输出契约

| Skill | 输入 | 输出 |
|---|---|---|
| DataPreviewSkill | 文件路径/数据库配置/多模态资料、用户提示词 | 原始表或清洗后的二维表、列类型、数据摘要、数据质量问题、可用于绘图的字段信息 |
| ChartPlanSkill | 用户提示词、数据摘要、对话历史、RAG 参考文档 | 一个或多个结构化图表计划，包含类型、标题、字段、变换、布局和数量约束 |
| ChartGenerateSkill | 图表计划、数据读取上下文、用户配置 | 可执行 Pyecharts 代码、执行结果、HTML 路径、错误信息和重试记录 |

### 5.3 关键设计约束

1. **LangChain 是编排框架**：模型调用、提示词模板、工具调用、记忆管理统一走 LangChain，不散落在各业务模块。
2. **中心 Agent 不直接写图表代码**：中心 Agent 负责调度和汇总，具体数据处理、规划和生成由对应 Skill 完成。
3. **RAG 是增强而非唯一依赖**：检索结果用于提高代码准确性；检索失败时仍要能生成基础图表。
4. **Pyecharts 是图表实现库**：生成代码使用 Pyecharts，图表结果落成独立 HTML。
5. **MCP Code 是执行通道**：生成代码通过 MCP 服务的 Code 工具执行，执行结果和错误回传到主流程。
6. **记忆分层**：短期消息队列、中期结构化总结与压缩、长期文件存储，三层职责不能混用。
7. **配置外置**：模型服务、数据库连接、路径、RAG 参数等通过配置或前端设置提供，不硬编码在业务代码里。
8. **可追溯**：每次任务的关键输入、计划、代码、执行结果和错误都能在日志或产物中找到。

### 5.4 技术选型

| 类别 | 选型 | 说明 |
|---|---|---|
| 后端语言 | Python | 主要开发语言 |
| LLM 编排 | LangChain | 链式调用、工具、记忆、提示词管理 |
| 提示词模板 | ChatPromptTemplate | 管理系统角色、用户输入、历史和参考文档 |

| Embedding | Qwen Embedding 0.6B | 本地生成文本向量 |
| 向量数据库 | Chroma | 本地持久化与语义检索 |

## 6. 相关研究设计经验与落地

开题报告在“研究进展”中梳理了数据可视化自然语言接口（DV-NLI）的几条技术路线。这些论文不只是研究背景，其中可复用的设计直接决定本项目的 Skill 划分、图表计划中间表示、RAG、记忆和交互方式。本项目不逐篇复现论文原型，而是抽取其设计原则，落到具体需求和架构中。表中的编号沿用开题报告参考文献序号，本文不重复列参考文献列表。逐篇分析、取舍理由、数据契约和系统设计见 `docs/论文参考与系统设计.md`。

### 6.1 论文设计方法对照

| 论文/系统 | 可复用的核心设计 | 本项目落地方式 | 对应需求 |
|---|---|---|---|
| **DataTone**[7] | 语义解析 + 启发式规则；重点处理自然语言查询中的歧义管理。 | ChartPlanSkill 先做意图解析；需求不完整时采用合理默认并说明，无法安全推断时追问；计划校验通过后才生成代码。 | FR-15、FR-20、FR-21 |
| **NL4DV**[8] | 把自然语言查询转成标准化的可视化分析规范，提供可复用的分析中间层。 | 定义结构化 chart plan，包含图表类型、字段、变换、排序、布局和多图关系；以计划作为 Skill 之间的契约，而不是让模型从原始提示词直接跳到代码。 | FR-17、FR-21、5.2 |
| **Chat2VIS**[9] | 端到端自然语言到可视化代码；利用大模型处理模糊、格式错误的查询，强调生成鲁棒性。 | ChartGenerateSkill 生成 Pyecharts 代码；增加输出清理、代码校验、异常重试、失败代码保留和代码编辑器查看，避免只做“一次性生成”。 | FR-24、FR-28、FR-43、FR-44、FR-61 |
| **VOICE**[11] | 大语言模型会话与交互式探索性可视化结合；支持语音、文本多模态；用户可用自然语言持续控制可视化过程。 | 采用多轮探索式交互，用户可在上一轮图表上继续修改；首版以文本输入为主，语音作为可选扩展，不把语音列为验收硬指标。 | FR-46、FR-59、FR-63 |
| **C5**[12] | 优化会话上下文连续性，缓解多轮交互中的上下文遗忘。 | 实现三层记忆：短期消息队列、中期结构化总结与上下文压缩、长期文件存储；支持会话恢复和任务隔离。 | FR-47、FR-48、FR-49、FR-50 |
| **RGVisNet**[13] | 检索 + 生成的混合框架：先从资源库检索相关可视化方案，再结合用户需求修订，提升生成准确性。 | 生成前用 Qwen Embedding 0.6B + Chroma 检索可视化代码示例，把相关示例注入提示词；检索失败时降级为无参考生成，不阻断主流程。 | FR-33—FR-39 |
| **FlowSense**[14] | 自然语言接口与数据流系统融合，把可视化数据探索流程化、自动化。 | 把 DataPreviewSkill → ChartPlanSkill → ChartGenerateSkill 串成显式工作流；阶段间传结构化状态；日志按阶段记录，支持定位任务卡点。 | 2.1、3.8、FR-51—FR-55、FR-68 |
| **NVAGENT**[15] | 多智能体协作工作流，完成自然语言到可视化的全流程自动化，强调多模块协同。 | 采用中心 Agent + Skill 的任务调度和失败隔离；借鉴多模块协同思想，但不追求自由的多智能体群聊，优先保证流程可控、可测试、可追踪。 | FR-51—FR-56 |

### 6.2 从论文设计提炼出的原则

1. **先规范、后生成**（NL4DV、RGVisNet）
   - 自然语言不能直接变成代码，必须先形成可校验的图表计划，再检索参考示例，最后生成代码。
   - 这样可以把“理解错需求”“选错图表”“代码写错”分开定位。

2. **歧义显式化**（DataTone）
   - 用户说“画个图看看”时，系统要结合数据形态给出合理默认，并说明选择了什么。
   - 字段、指标或时间范围存在多种解释且会影响结果时，应追问，不能静默猜测。

3. **检索增强、可降级**（RGVisNet）
   - RAG 用于提高复杂图表和陌生 API 的生成准确率，是增强项，不是单点依赖。
   - 知识库不可用、检索为空或 embedding 失败时，仍要能生成基础图表，并在日志中说明降级原因。

4. **会话连续性与探索式修改**（C5、VOICE）
   - 多轮对话要保留上一轮的数据、计划、图表和用户约束。
   - 用户说“改成柱状图”“只看前五名”时，不应要求重新上传数据或重复完整描述。
   - 上下文过长时通过结构化总结和压缩控制 token，不能简单截断导致关键约束丢失。

5. **流程编排与可追溯**（FlowSense、NVAGENT）
   - 数据预览、图表计划、代码生成、执行和落盘是明确阶段，不是一次模型调用。
   - 每个阶段有输入、输出、错误和状态；单阶段失败可定位、可重试，不破坏已完成结果。

6. **工程化优先于论文原型复刻**
   - 论文原型通常重点验证交互或生成方法；本项目还要落地 WinUI 桌面端、MCP 代码执行、配置管理、日志、错误恢复和多模态数据接入。
   - 多智能体协作在本项目中收敛为“中心 Agent + Skill”，减少不可控的自由协作，便于测试和验收。
   - 语音交互借鉴 VOICE 的探索式会话思路，但首版以文本为主，避免把未明确要求的语音能力变成验收负担。

7. **质量评估不只看模型输出**
   - 论文常以生成结果或交互效果评估；本项目还要看数据是否读对、字段是否匹配、图表是否可读、HTML 是否可打开、是否满足响应时间和 token 上限。
   - 验收同时覆盖功能、性能、智能水平、安全性和用户体验。

### 6.3 与论文原型的差异

| 维度 | 论文中的常见做法 | 本项目的工程化选择 |
|---|---|---|
| 系统形态 | 研究原型、Web 演示或工具包 | WinUI 桌面应用 + Python 后端 + MCP 代码执行 |
| 自然语言到图表 | 端到端生成，或先生成分析规范 | 先生成结构化 chart plan，再做 RAG 检索和代码生成 |
| 检索增强 | 检索相关可视化方案或代码 | 本地 Qwen Embedding 0.6B + Chroma 代码示例库，检索失败可降级 |
| 多模块协同 | 多智能体协作或数据流系统 | 中心 Agent + 三个核心 Skill，强调契约、失败隔离和可追踪 |
| 交互方式 | 文本、语音、可视化探索 | 首版文本输入 + 多轮修改 + HTML 交互预览；语音可选 |
| 数据输入 | 多以结构化表格为主 | 增加 CSV/Excel/数据库/代码文档/多模态表格抽取的统一接入 |
| 评估方式 | 生成质量、交互体验或基准测试 | 数据正确性、图表成功率、响应时间、token、安全性和桌面端可用性 |

### 6.4 对研究缺口的回应

开题报告指出：现有研究多聚焦模型本身的优化，针对 LLM 应用编排、多模块协同的可视化智能体开发仍有待完善。本项目的设计重点不是再训练一个可视化模型，而是把已有论文中的有效方法工程化组合起来：

- 用 **NL4DV** 的分析规范思想解决“需求和代码之间缺少中间层”的问题；
- 用 **DataTone** 的歧义管理思想解决“用户说不清、系统猜错”的问题；
- 用 **RGVisNet** 的检索增强思想解决“模型不熟悉 Pyecharts API、代码易错”的问题；
- 用 **C5 / VOICE** 的上下文与探索式交互思想解决“多轮修改不连贯”的问题；
- 用 **FlowSense / NVAGENT** 的流程与协同思想解决“多阶段任务缺少编排和追溯”的问题；
- 最终通过 LangChain、MCP、WinUI 和本地 RAG 把这些方法落成一个可运行、可测试、可扩展的桌面智能体。

## 7. 验收标准

### 7.1 功能验收场景

| 编号 | 场景 | 预期结果 |
|---|---|---|
| AC-01 | 上传 CSV，输入“按月份画销售额趋势” | 能识别月份和销售额字段，生成折线图或面积图，HTML 可预览，数据点与源数据一致。 |
| AC-02 | 上传含多个工作表、合并表头或标题行的 Excel | 能正确识别表头和数据区，跳过空白页/封面页，预览表头和行数正确。 |
| AC-03 | 配置数据库并选择表或查询 | 能连接数据库、读取结果并生成图表；连接失败时有明确错误。 |
| AC-04 | 上传表格截图、扫描 PDF 或带表格截图的 Office 文档 | 能抽取为二维表并进入预览；无法抽取时说明具体原因，不生成臆造数据。 |
| AC-05 | 输入“用饼图看各城市销售占比” | 图表类型为饼图，类别和数值与数据一致；用户显式指定的类型不被自动改掉。 |
| AC-06 | 在多轮对话中说“改成柱状图”“只看前五名” | 能结合上下文修改上一轮结果，不要求用户重复完整描述。 |
| AC-07 | 输入“画两个图：趋势和城市对比” | 生成不超过两张图，类型和数据角度合理，不重复出同一张图。 |
| AC-08 | 生成一个不常见图表类型或复杂样式 | RAG 能检索到相关示例并辅助生成；检索不到时仍能给出可理解的回退结果。 |
| AC-09 | 模型超时、代码报错或数据字段不存在 | 任务失败有明确错误信息，失败代码和日志可追踪；应用不崩溃，可继续提交新任务。 |
| AC-10 | 图表生成完成 | HTML 自动保存到指定目录，按数据文件名分类；应用内可预览，支持放大和悬停查看。 |
| AC-11 | 查看日志 | 能定位数据接入、规划、RAG 检索、代码生成、执行和落盘阶段；能看到耗时和错误。 |
| AC-12 | 更换模型服务或 API Key | 通过前端设置即可切换，不需要修改代码；配置不写入仓库。 |

### 7.2 性能与质量验收

| 编号 | 指标 | 验收方式 |
|---|---|---|
| AC-13 | 单次任务 ≤ 120 秒 | 选取代表性 CSV/Excel/数据库/多模态样例，记录从提交到 HTML 可预览的耗时。 |
| AC-14 | 单份任务 ≤ 0.3M token | 汇总单次任务全部模型调用的 token；超限时分析是提示词、历史还是重试导致。 |
| AC-15 | 代码生成成功率 ≥ 90% | 在固定测试集上统计成功渲染且数据字段正确的比例。 |
| AC-16 | Windows 10/11 可用 | 在两个系统版本上各完成一次完整流程。 |
| AC-17 | 安全性 | 检查 API Key/数据库密码是否出现在仓库或日志；验证代码执行超时、数据库只读和路径校验。 |

### 7.3 完成定义

满足以下条件才能视为开发完成：

- 主流程能稳定完成“数据接入 → 数据预览/清洗 → 图表规划 → 代码生成 → HTML 预览 → 保存”；
- CSV、Excel、数据库、多模态数据至少各有成功案例；
- 折线图、柱状图、饼图、散点图至少各有成功案例；
- RAG 检索、三层记忆、日志追溯、WinUI 工作区均可演示；
- 性能、token、成功率指标达到 NFR-01 至 NFR-03；
- 错误路径有明确提示和日志，不出现静默失败；
- 关键模块有可重复执行的测试或验收脚本。

## 8. 范围、假设与待确认事项

### 8.1 本文不包含的内容

- 纯研究背景、文献综述和论文罗列（其中可复用的论文设计已提炼到第 6 节）；
- 研究进度安排、时间节点和答辩计划；
- 参考文献列表；
- 论文写作、排版和答辩材料。

### 8.2 当前假设

1. 首版按**单用户、本地桌面应用**设计，不要求多租户、云端部署和复杂权限系统。
2. 大模型可以调用云端 OpenAI 兼容服务；RAG 的 embedding 和向量库在本地运行。
3. 用户可以接受首次使用前进行模型配置或知识库准备。
4. 图表以独立 HTML 为主要交付物，不要求嵌入现有 BI 平台。
5. 数据库至少支持一种常见关系型数据库，具体方言和驱动在实现阶段确定。

### 8.3 需要确认的实现细节

| 事项 | 需要确认的内容 |
|---|---|
| 数据库范围 | 具体支持 MySQL、PostgreSQL、SQLite 中的哪些方言；是否需要自定义 SQL。 |
| “代码文档”范围 | 具体支持哪些代码/文档扩展名，如何从代码文件中提取可表格化数据。 |
| 多模态格式 | 图片、PDF、Office 文档的具体扩展名、页数/大小上限和失败回退策略。 |
| 图表类型全集 | 除折线图、柱状图、饼图、散点图外，是否需要柱状图分组/堆叠、面积图、热力图、矩形树图等。 |
| 图表计划确认 | 生成代码前是否需要用户确认计划，还是默认自动执行。 |
| 代码编辑器能力 | 只读查看还是允许编辑并重新执行；编辑后的代码是否参与后续多轮修改。 |
| 会话隔离 | 不同工作区、不同数据文件的会话如何隔离和清理。 |
| 打包方式 | 单文件、安装包还是开发环境运行；是否需要内置 Python/依赖。 |
| 安全边界 | 数据库是否强制只读、代码执行允许访问哪些路径、是否允许联网。 |
| 性能测量条件 | 120 秒是否包含大文件上传、模型冷启动、RAG 首次建库。 |
