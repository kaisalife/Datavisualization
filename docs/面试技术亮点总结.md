# DataVisualServer — 智能体开发岗位面试总结

## 一句话概述

> 基于 LangChain + MCP 协议的数据可视化智能体系统，支持多源数据接入（文件/数据库/API）、LLM 自主规划图表方案、沙箱执行 + 自动调试、RAG 知识库复用，端到端从自然语言需求到可视化报告。

---

## 技术亮点（面试重点讲）

### 1. 智能体架构设计

**BaseAgent + MCP 工具系统**

- 设计 `BaseAgent`（继承 LangChain `Runnable`），封装 LLM 调用 + MCP 工具加载，两阶段懒初始化（构造只存参数，`async initialize()` 才建连接）
- 通过 `MultiServerMCPClient` 连接 MCP 子进程，实现工具服务化隔离
- **fail-closed 安全设计**：工具默认需确认、默认非只读、默认非并发安全 — 安全属性默认值均为最安全选项
- **工具池稳定排序**：按 name 字母序排序，防止 LLM prompt cache 失效（精细化性能优化）

### 2. LLM 重试策略（企业级容错）

- **异常分类体系**：6 种异常类型（限流/上下文溢出/认证/服务端/超时/连接），可重试 vs 不可重试自动判断
- **前后台任务区分**：前台任务（生成/规划）重试 5 次，后台任务（记忆/摘要）只重试 1 次快速放弃
- **指数退避 + 抖动**：`wait_exponential_jitter(initial=1, max=20)`，避免惊群效应
- **统一异常映射**：openai/langchain/原生异常自动分类，还支持基于错误消息文本的兜底

### 3. 数据适配层（六边形架构实践）

**防腐层 + 两阶段 Adapter 模式**

- `VizDataset` 统一数据契约：文件/数据库/API 全部归一化为同一格式
- **fetch + normalize 两阶段**：fetch 阶段处理不确定性（LLM 调用、网络请求、脏数据），normalize 是纯函数（可测试、可缓存、幂等）
- **注册表模式**：`@register_source` 装饰器注册数据源，新增数据源零修改工厂代码（开闭原则）
- **端口协议**：`typing.Protocol` 声明契约，支持 Fake/Mock 替身，DatabaseAdapter 不直接依赖 LLM prompts
- 支持 6 种数据源：CSV/Excel/Parquet/JSON/PDF/数据库，多文件智能列对齐合并

### 4. 并发图表生成流水线

```
用户需求 -> LLM 规划 N 张图表 -> asyncio.gather 并发生成 -> 每张独立调试重试
```

- **Semaphore 并发控制**：限制同时执行的图表生成数，防止资源耗尽
- **生成-执行-调试循环**：首次用 `generate_prompt`，失败后用 `debug_prompt`（传入上轮错误），最多重试 N 次
- **沙箱执行**：AST 安全扫描 + subprocess 隔离 + 60s 超时
- `return_exceptions=True`：单个图表失败不影响全局

### 5. RAG 知识库

- **Chroma 向量库** + `Qwen3Embeddings` 本地嵌入模型
- 懒加载：已有持久化目录直接加载，否则从文档构建
- 图表生成前检索历史成功模板，提高生成质量和速度

### 6. 任务管理 + 实时通信

- **取消机制**：`_cancelled_tasks` set + 5 个检查点，支持中途取消 LLM 任务
- **WebSocket 主动推送**：flask_sock 连接池管理，任务完成实时通知，前端无需轮询
- **线程池执行**：Flask 请求线程提交到 ThreadPoolExecutor，每线程独立事件循环
- **SQLite 对话持久化**：WAL 模式 + 索引优化，完整记录每次对话的输入/输出/日志

## 面试问答准备

### Q: 你在智能体设计中如何处理安全性？

**A:** 采用了 fail-closed 设计原则。工具基类的安全属性默认值均为最安全值：默认非只读、默认需确认、默认非并发安全。`PermissionDecision` 三级决策（ALLOW/DENY/CONFIRM）。代码执行通过 AST 安全扫描 + subprocess 隔离 + 超时控制三重防护。

### Q: LLM 调用不稳定怎么办？

**A:** 设计了企业级重试策略。首先异常分类 — 6 种异常类型，区分可重试（限流/超时/连接）和不可重试（认证/上下文溢出）。其次前后台任务区分 — 前台任务重试 5 次，后台任务只重试 1 次快速放弃。退避策略用指数退避+抖动避免惊群。

### Q: 如何保证数据适配层的可测试性？

**A:** 采用六边形架构 + 两阶段 Adapter 模式。fetch 阶段处理所有不确定性（LLM 调用、网络请求），normalize 是纯函数 — 禁止 IO、禁止 LLM、必须幂等。通过 `typing.Protocol` 声明端口契约，支持 Fake/Mock 替身，DatabaseAdapter 不直接依赖 LLM prompts。

### Q: 多个图表如何高效生成？

**A:** asyncio.gather 并发执行 + Semaphore 控制并发度。每张图表独立的"生成-执行-调试"循环：首次用 generate_prompt，失败后用 debug_prompt 传入上轮错误信息。return_exceptions=True 确保单个失败不影响全局。

### Q: 如何处理工具调用的 prompt cache 优化？

**A:** 工具池按 name 字母序稳定排序。LLM 的 prompt cache 对工具定义部分的位置敏感，如果工具顺序变化会导致 cache 失效。`assemble_tool_pool` 函数强制排序，确保相同工具集总是以相同顺序出现在 prompt 中。
